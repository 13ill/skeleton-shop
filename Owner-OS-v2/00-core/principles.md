# หลักคิด 10 ข้อ ของ AI-Native Operator

> หลักการตัดสินใจและทำงานแบบ Business Owner

---

## 🎯 ทำไมต้องมีหลักคิด?

หลักคิดเหล่านี้จะช่วยให้คุณ:
- ตัดสินใจได้ดีขึ้น
- คิดเหมือน owner ไม่ใช่แค่ dev
- หลีกเลี่ยงกับดักทั่วไป
- เติบโตเป็น Business Owner

---

## 1️⃣ Think Before Act (คิดก่อนทำ)

### ความหมาย
ห้ามรีบทำทันที ต้องผ่าน Gate System ก่อนเสมอ

### ทำไมสำคัญ?
- การรีบทำ = พลาดรายละเอียด
- พลาดรายละเอียด = ทำผิด
- ทำผิด = เสียเวลามากกว่า

### ตัวอย่าง
```
❌ ผิด:
User: "ทำระบบ login"
Dev: เขียนโค้ดทันที

✅ ถูก:
User: "ทำระบบ login"
Dev: ถามก่อน
  - ต้องรองรับ social login ไหม?
  - ต้องมี forgot password ไหม?
  - ต้องมี 2FA ไหม?
  - session timeout เท่าไหร่?
```

### วิธีใช้
- ผ่าน Gate 0-5 ก่อนเขียนโค้ด
- ถามคำถามให้ครบ
- ได้ requirement ชัดเจนก่อน

---

## 2️⃣ System Thinking (คิดเชิงระบบ)

### ความหมาย
ทุกอย่างเชื่อมโยงกัน ต้องมอง upstream/downstream/dependency

### ทำไมสำคัญ?
- แก้ตรงนี้ อาจพังตรงโน้น
- เพิ่ม feature นี้ อาจกระทบระบบอื่น

### ตัวอย่าง
```
งาน: เปลี่ยน stock calculation logic

System Thinking:
- Upstream: POS ส่งข้อมูลมาอย่างไร?
- Downstream: Reports ใช้ข้อมูลนี้ไหม?
- Dependency: มี module ไหนพึ่งพา stock?
- Impact: ถ้าพัง จะกระทบอะไรบ้าง?
```

### วิธีใช้
- ถามเสมอ: "ถ้าพัง จะเกิดอะไร?"
- เช็ค upstream/downstream
- เช็ค dependency
- มี rollback plan

---

## 3️⃣ Ask Before Assume (ถามก่อนเดา)

### ความหมาย
ถ้าไม่แน่ใจ ถามกลับ ห้ามเดา

### ทำไมสำคัญ?
- เดาผิด = ทำผิด
- ทำผิด = ทำใหม่
- ทำใหม่ = เสียเวลา 2 เท่า

### ตัวอย่าง
```
❌ ผิด:
User: "เพิ่ม feature ส่วนลด"
Dev: เดาเองว่าส่วนลดคือ % → เขียนโค้ด
Owner: "ฉันต้องการทั้ง % และ บาท"
Dev: ทำใหม่ทั้งหมด

✅ ถูก:
User: "เพิ่ม feature ส่วนลด"
Dev: ถาม
  - ส่วนลดเป็น % หรือ บาท?
  - ส่วนลดสูงสุดเท่าไหร่?
  - ใช้ได้กับสินค้าทั้งหมดหรือเฉพาะบางอย่าง?
  - มีเงื่อนไขอะไรบ้าง?
```

### วิธีใช้
- ถ้า requirement ไม่ชัด → ถามกลับ
- ถ้าไม่แน่ใจ → ถามกลับ
- ถ้ามีหลายทางเลือก → ถามว่าต้องการทางไหน

---

## 4️⃣ Options with Tradeoffs (เสนอทางเลือกพร้อมข้อแลกเปลี่ยน)

### ความหมาย
ไม่มีทางเดียว ต้องมี 2-3 ทางเลือก พร้อมวิเคราะห์ข้อดี/ข้อเสีย

### ทำไมสำคัญ?
- ทุกอย่างมี tradeoff
- ทางที่ดีที่สุด = ทางที่เหมาะสมกับ context
- Owner ต้องเลือกเอง

### ตัวอย่าง
```
งาน: เลือก database

ทาง A: PostgreSQL
- ✅ ข้อดี: Relational, ACID, ทดสอบมาแล้ว
- ❌ ข้อเสีย: ช้ากว่า NoSQL, scale ยากกว่า
- 💰 ราคา: ฟรี (self-hosted) หรือ $25/mo (managed)
- 🎯 เหมาะกับ: ข้อมูลมี relation ชัดเจน

ทาง B: MongoDB
- ✅ ข้อดี: เร็ว, flexible schema, scale ง่าย
- ❌ ข้อเสีย: ไม่มี ACID, ยาก query ข้อมูลที่ซับซ้อน
- 💰 ราคา: ฟรี (self-hosted) หรือ $57/mo (Atlas)
- 🎯 เหมาะกับ: ข้อมูลไม่มี relation มาก, ต้องการ scale

แนะนำ: PostgreSQL (เพราะข้อมูลมี relation ชัดเจน)
```

### วิธีใช้
- เสนอ 2-3 ทางเลือก
- วิเคราะห์ข้อดี/ข้อเสีย/ราคา/เหมาะกับ
- แนะนำทาง + เหตุผล
- ให้ owner เลือก

## 5️⃣ Document Everything (บันทึกทุกอย่าง)

### ความหมาย
Decision, Lesson, Investigation ต้อง log ทุกครั้ง

### ทำไมสำคัญ?
- ลืมได้ แต่ log ไม่ลืม
- คนใหม่มาอ่าน log เข้าใจได้
- ทำผิดซ้ำไม่ได้ (ถ้าอ่าน lesson log)

### ตัวอย่าง
```
Decision Log:
- เลือก PostgreSQL
- เพราะ: ข้อมูลมี relation ชัดเจน
- ยอมรับ: ช้ากว่า NoSQL
- วันที่: 2026-05-31

Lesson Log:
- เรียนรู้: ต้อง setup test database ก่อนเขียน tests
- เพราะ: เสียเวลา 1 ชม. เพราะไม่มี test DB
- ครั้งหน้า: setup test DB ใน Gate 6 (Planning)
```

### วิธีใช้
- ตัดสินใจ → เขียน decision log
- เรียนรู้ → เขียน lesson log
- สืบค้น → เขียน investigation log
- AI จะเขียนให้อัตโนมัติ

## 6️⃣ Fail Fast, Learn Fast (ล้มเร็ว เรียนเร็ว)

### ความหมาย
ทดสอบเร็ว ถ้าผิดก็รู้เร็ว แก้เร็ว

### ทำไมสำคัญ?
- ล้มช้า = เสียเวลามาก
- ล้มเร็ว = เสียเวลาน้อย
- เรียนรู้เร็ว = ไม่ทำผิดซ้ำ

### ตัวอย่าง
```
❌ ผิด:
เขียนโค้ด 1 สัปดาห์ → ทดสอบ → พบว่าผิด → ทำใหม่ทั้งหมด

✅ ถูก:
เขียนโค้ด 1 วัน → ทดสอบ → พบว่าผิด → แก้ทันที
เขียนต่อ 1 วัน → ทดสอบ → ถูก → เขียนต่อ
```

### วิธีใช้
- เขียน tests ก่อนเขียนโค้ด (TDD)
- ทดสอบบ่อยๆ
- Deploy staging บ่อยๆ
- ได้ feedback เร็ว

---

## 7️⃣ Prevention Over Cure (ป้องกันดีกว่าแก้)

### ความหมาย
ป้องกันปัญหาก่อนเกิด ดีกว่าแก้หลังเกิด

### ทำไมสำคัญ?
- แก้ปัญหา = เสียเวลา
- ป้องกัน = ไม่เสียเวลา
- ป้องกันถูกกว่าแก้

### ตัวอย่าง
```
Prevention:
- เขียน tests → ป้องกัน bug
- Code review → ป้องกัน bad code
- Monitoring → ป้องกัน downtime
- Backup → ป้องกัน data loss

Cure:
- แก้ bug → เสียเวลา
- Refactor → เสียเวลา
- Restore → เสียเวลา
```

### วิธีใช้
- เขียน tests ทุกครั้ง
- Code review ก่อน merge
- Setup monitoring
- Backup อัตโนมัติ

---

## 8️⃣ Leverage (ใช้ประโยชน์จาก AI)

### ความหมาย
งานซ้ำๆ ให้ AI ทำ คุณทำงานที่ต้องคิด

### ทำไมสำคัญ?
- เวลาจำกัด
- AI ทำงานซ้ำได้เร็วกว่า
- คุณควรโฟกัสที่งานที่ต้องคิด

### ตัวอย่าง
```
ให้ AI ทำ:
- เขียน boilerplate code
- เขียน tests
- เขียน documentation
- Generate types
- Refactor code

คุณทำ:
- ออกแบบ architecture
- ตัดสินใจ
- Review code
- คิด business logic
```

### วิธีใช้
- ใช้ Tower Control (สั่งงาน AI หลายตัว)
- ให้ AI ทำงานซ้ำ
- คุณ review + approve

## 9️⃣ Owner Mindset (คิดเหมือนเจ้าของ)

### ความหมาย
คิดเหมือนเจ้าของธุรกิจ ไม่ใช่แค่ dev

### ทำไมสำคัญ?
- Dev คิดแค่ทำงานให้เสร็จ
- Owner คิดถึง business value, ROI, risk

### ตัวอย่าง
```
Dev Mindset:
- ทำงานให้เสร็จ
- ตาม spec
- ไม่สนใจ business

Owner Mindset:
- งานนี้สร้าง value อะไร?
- ROI คุ้มไหม?
- มีความเสี่ยงอะไร?
- ถ้าไม่ทำจะเกิดอะไร?
- มีทางเลือกอื่นที่ดีกว่าไหม?
```

### วิธีใช้
- ถามเสมอ: "งานนี้สร้าง value อะไร?"
- คิด ROI
- คิด risk
- คิด opportunity cost

## 🔟 Measurable (วัดผลได้)

### ความหมาย
Success criteria ต้องวัดได้ ไม่ใช่คลุมเครือ

### ทำไมสำคัญ?
- วัดไม่ได้ = ไม่รู้ว่าสำเร็จหรือไม่
- วัดได้ = รู้ว่าต้องทำอะไร

### ตัวอย่าง
```
❌ ผิด (คลุมเครือ):
- ระบบต้องเร็ว
- ระบบต้องดี
- User ต้องพอใจ

✅ ถูก (วัดได้):
- Response time < 200ms
- Uptime > 99.9%
- NPS > 50
- Conversion rate > 5%
```

### วิธีใช้
- กำหนด success criteria ที่วัดได้
- ใช้ตัวเลข
- ตั้ง KPI
- Track metrics
