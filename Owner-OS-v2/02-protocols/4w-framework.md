# 4W Framework — WHY / WHAT / HOW / WHEN

> กรอบคิดพื้นฐานที่ต้องตอบให้ครบก่อนเริ่มทำงาน

---

## 🎯 วัตถุประสงค์

ก่อนเริ่มงานใดๆ ต้องตอบ 4 คำถามนี้ให้ครบและชัดเจน:

1. **WHY** — ทำไมต้องทำ?
2. **WHAT** — ทำอะไร?
3. **HOW** — ทำยังไง?
4. **WHEN** — ทำเมื่อไหร่?

**ลำดับสำคัญ:** ต้องตอบ **WHY ก่อน WHAT ก่อน HOW** เสมอ
ห้ามกระโดดไป HOW (solution) ก่อนเข้าใจ WHY (ปัญหา)

---

## 1️⃣ WHY — ทำไมต้องทำ?

> **นี่คือคำถามที่สำคัญที่สุด — ต้องตอบก่อนเสมอ**

### คำถามที่ต้องตอบ

- ทำไปทำไม? แก้ปัญหาอะไร?
- ถ้าไม่ทำจะเกิดอะไร? (cost of inaction)
- ใครได้ประโยชน์? ได้ประโยชน์อะไร?
- คุ้มค่าไหม? (ROI)

### Map กับ Gate

→ **Gate 1: Business Understanding**

### ตัวอย่าง

```
งาน: "ทำระบบแจ้งเตือนสต็อกต่ำ"

WHY ที่ดี:
- ปัญหา: ของหมดสต็อกบ่อย ทำให้ขายไม่ได้ เสียยอด 50,000 บาท/เดือน
- ถ้าไม่ทำ: เสียลูกค้า เสียยอดขายต่อเนื่อง
- ผู้ได้ประโยชน์: เจ้าของร้าน (ไม่เสียยอด), ลูกค้า (มีของซื้อ)
- ROI: ลงทุน 3 วัน ประหยัดได้ 50,000 บาท/เดือน = คุ้มมาก

WHY ที่ไม่ดี:
- "อยากได้" ← ไม่มีเหตุผลทางธุรกิจ
- "เห็นร้านอื่นมี" ← ตามคนอื่นโดยไม่คิด
```

---

## 2️⃣ WHAT — ทำอะไร?

> นิยามขอบเขตให้ชัด ป้องกัน scope creep

### คำถามที่ต้องตอบ

- ทำอะไรบ้าง? (in scope)
- ไม่ทำอะไรบ้าง? (out of scope)
- Deliverable คืออะไร?
- Success criteria ที่วัดได้คืออะไร? (KPI)

### Map กับ Gate

→ **Gate 0: Task Intake**

### ตัวอย่าง

```
งาน: "ทำระบบแจ้งเตือนสต็อกต่ำ"

WHAT ที่ดี:
- In scope: แจ้งเตือนผ่าน LINE เมื่อสต็อก < threshold
- Out of scope: auto-reorder, การพยากรณ์ความต้องการ
- Deliverable: ระบบแจ้งเตือน + หน้าตั้งค่า threshold
- KPI: ลดเหตุการณ์ของหมดสต็อกจาก 10 ครั้ง/เดือน → 0 ครั้ง

WHAT ที่ไม่ดี:
- "ทำระบบสต็อก" ← กว้างเกิน ไม่รู้ขอบเขต
```

---

## 3️⃣ HOW — ทำยังไง?

> **ห้ามมาขั้นนี้ก่อนตอบ WHY และ WHAT ให้ครบ**

### คำถามที่ต้องตอบ

- มีกี่ทางเลือก? (ต้องมี 2-3 ทาง)
- แต่ละทาง tradeoff คืออะไร?
- เลือกทางไหน? เพราะอะไร?
- Tech stack / architecture คืออะไร?

### Map กับ Gate

→ **Gate 4: Solution Design** + **Gate 5: Decision**

### ตัวอย่าง

```
งาน: "ทำระบบแจ้งเตือนสต็อกต่ำ"

HOW ที่ดี (มีหลายทางเลือก):
ทาง A: Cron job เช็คทุกชั่วโมง
- ✅ ง่าย, ทำเร็ว
- ❌ ดีเลย์สูงสุด 1 ชม.

ทาง B: Event-driven (เช็คทุกครั้งที่ขาย)
- ✅ Real-time
- ❌ ซับซ้อนกว่า

เลือก: ทาง A (เพราะดีเลย์ 1 ชม. ยอมรับได้ และทำเร็ว)

HOW ที่ไม่ดี:
- กระโดดเขียนโค้ดเลยโดยไม่เทียบทางเลือก
```

---

## 4️⃣ WHEN — ทำเมื่อไหร่?

> วางแผนเวลาและลำดับความสำคัญ

### คำถามที่ต้องตอบ

- Deadline เมื่อไหร่?
- ใช้เวลาเท่าไหร่? (estimation)
- Priority แค่ไหน? (เทียบกับงานอื่น)
- ทำตอนนี้เลย หรือรอ?

### Map กับ Gate

→ **Gate 6: Planning**

### ตัวอย่าง

```
งาน: "ทำระบบแจ้งเตือนสต็อกต่ำ"

WHEN ที่ดี:
- Deadline: ภายใน 1 สัปดาห์
- Estimation: 3 วัน (best 2 / likely 3 / worst 5)
- Priority: High (เพราะเสียยอดทุกวัน)
- เริ่มเลย: ใช่ (ROI สูง, urgent จริง)

WHEN ที่ไม่ดี:
- "ทำเมื่อว่าง" ← ไม่มีแผน ไม่มี priority
```

---

## 🔄 ลำดับการตอบ 4W

```
WHY (ทำไม)
  ↓ ต้องชัดก่อน
WHAT (ทำอะไร)
  ↓ ต้องชัดก่อน
HOW (ทำยังไง)
  ↓ ต้องชัดก่อน
WHEN (ทำเมื่อไหร่)
```

**กฎเหล็ก:**
- ❌ ห้ามตอบ HOW ก่อน WHY/WHAT
- ❌ ห้ามเสนอ solution ก่อนนิยามปัญหา
- ✅ ตอบตามลำดับ WHY → WHAT → HOW → WHEN

---

## ✅ 4W Checklist

ก่อนเริ่มเขียนโค้ด ต้องตอบครบ:

- [ ] **WHY** — รู้ว่าทำไมต้องทำ (มีเหตุผลทางธุรกิจ)
- [ ] **WHY** — รู้ว่าถ้าไม่ทำจะเกิดอะไร
- [ ] **WHAT** — รู้ขอบเขตชัดเจน (in/out scope)
- [ ] **WHAT** — มี KPI ที่วัดได้
- [ ] **HOW** — มีอย่างน้อย 2-3 ทางเลือก
- [ ] **HOW** — เลือกทางพร้อมเหตุผล
- [ ] **WHEN** — มี deadline และ estimation
- [ ] **WHEN** — รู้ priority
