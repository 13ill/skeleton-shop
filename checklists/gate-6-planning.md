# Gate 6 — Planning: วางแผนการทำงาน

## วัตถุประสงค์
แตกงานใหญ่ออกเป็น **ชิ้นเล็กๆ ที่จัดการได้** พร้อมลำดับและ checkpoint
Gate นี้ป้องกันการ "ทำไปเรื่อยๆ ไม่รู้ว่าอยู่ตรงไหน"

> ปัญหาที่พบบ่อย: เริ่มเขียนโค้ดเลยโดยไม่มีแผน
> ผลคือทำไปครึ่งทางแล้วหลงทาง ไม่รู้ว่าเหลือเท่าไหร่ ไม่รู้ว่าไปถูกทางไหม

==================================================

## คำถามที่ต้องถามตัวเอง

### 1. "แตก task เป็นชิ้นเล็กได้อย่างไร?"
- **ทำไมต้องถาม**: Task ใหญ่ = มองไม่เห็นภาพ = ประมาณเวลาไม่ได้ = หลงทางง่าย
- **สิ่งที่ได้**: Task list ที่แต่ละชิ้นทำเสร็จได้ใน 1-4 ชั่วโมง
- **เกณฑ์แตก task ที่ดี**:
  - แต่ละ task มี input ชัดเจน + output ชัดเจน
  - แต่ละ task test ได้เป็นอิสระ
  - แต่ละ task ไม่เกิน 4 ชั่วโมง
  - แต่ละ task อธิบายด้วย 1 ประโยคได้
- **ตัวอย่าง**: "ทำระบบ authentication" แตกเป็น:
  1. สร้าง User model + migration (1 ชม.)
  2. สร้าง registration API (2 ชม.)
  3. สร้าง login API + JWT generation (2 ชม.)
  4. สร้าง auth middleware (1 ชม.)
  5. เขียน tests สำหรับ auth flow (2 ชม.)

### 2. "อะไรต้องทำก่อน — Dependencies เป็นอย่างไร?"
- **ทำไมต้องถาม**: ถ้าทำผิดลำดับ → ต้อง rework (ทำซ้ำ) ถ้าทำ task ที่ depend (พึ่งพา) task อื่นก่อน → ติด
- **สิ่งที่ได้**: ลำดับงานที่ถูกต้อง → ไม่ถูก block
- **คำอธิบาย**: Dependencies (การพึ่งพา) คือ task ที่ต้องเสร็จก่อนจึงจะเริ่ม task ถัดไปได้
- **ตัวอย่าง**: ต้องสร้าง DB schema ก่อน → จึงเขียน API ได้ → จึงเขียน frontend ได้

### 3. "Milestone อยู่ตรงไหน?"
- **ทำไมต้องถาม**: Milestone (จุดตรวจสอบ) คือจุดที่สามารถหยุดดูได้ว่ากำลังไปถูกทางไหม
- **สิ่งที่ได้**: จุดตรวจสอบ → ไม่ต้องรอถึงจุดสุดท้ายจึงจะรู้ว่าผิดทาง
- **ตัวอย่าง**: 
  - Milestone 1: Database + API พร้อม (demo ได้ด้วย Postman)
  - Milestone 2: Frontend เชื่อม API ได้ (demo ได้ด้วย browser)
  - Milestone 3: ทุก test ผ่าน + deploy staging สำเร็จ

### 4. "Definition of Done ของแต่ละ task คืออะไร?"
- **ทำไมต้องถาม**: ถ้าไม่มี → ทำไม่จบ หรือทำแล้วไม่มั่นใจว่าเสร็จ
- **สิ่งที่ได้**: เกณฑ์ที่ชัดเจนว่า "เสร็จ" คืออะไร
- **คำอธิบาย**: Definition of Done (DoD — เกณฑ์ว่าเสร็จ) คือเงื่อนไขที่ต้องเกิดขึ้นทุกข้อจึงจะถือว่า task นั้นเสร็จ
- **ตัวอย่าง DoD สำหรับแต่ละ task**:
  - โค้ดเขียนเสร็จ
  - Tests ผ่านทั้งหมด
  - Code review ผ่าน (ถ้าทำเป็นทีม)
  - Documentation อัพเดท (ถ้าจำเป็น)
  - ทำงานได้ใน staging environment

### 5. "ประมาณเวลาเท่าไหร่ — Estimate เป็นอย่างไร?"
- **ทำไมต้องถาม**: ประมาณเวลาเพื่อวางแผนและสื่อสารกับ stakeholder
- **สิ่งที่ได้**: Timeline ที่สมจริง
- **เทคนิคประมาณเวลา**:
  - คิดเวลาที่คาดว่าจะใช้ → คูณ 1.5-2x (เผื่อ unknowns)
  - ถ้าไม่เคยทำมาก่อน → คูณ 2-3x
  - ถ้ามี external dependencies → เผื่อเวลารอ
- **ตัวอย่าง**: คิดว่าใช้ 2 วัน → ประมาณ 3-4 วัน → สื่อสารว่า "3-4 วัน"

### 6. "Testing strategy เป็นอย่างไร?"
- **ทำไมต้องถาม**: ถ้าไม่มีแผน test → ไม่รู้ว่าพังเมื่อไหร่
- **สิ่งที่ได้**: แผนการ test ที่ครอบคลุม
- **ประเภท test ที่ต้องคิด**:
  - Unit tests (ทดสอบทีละ function/method)
  - Integration tests (ทดสอบว่าหลาย components ทำงานร่วมกันได้)
  - E2E tests (End-to-End — ทดสอบ flow ทั้งหมดจาก user perspective)
  - Manual testing (ทดสอบด้วยมือ)

### 7. "Deployment strategy เป็นอย่างไร?"
- **ทำไมต้องถาม**: deploy ผิดวิธี → production พัง
- **สิ่งที่ได้**: แผน deploy ที่ปลอดภัย
- **ทางเลือก**:
  - Big bang (deploy ทีเดียวทั้งหมด): ง่าย แต่เสี่ยง
  - Progressive rollout (deploy ทีละส่วน): ปลอดภัยกว่า แต่ซับซ้อนกว่า
  - Feature flag (เปิด-ปิด feature): ปลอดภัยที่สุด แต่ต้องจัดการ flags
  - Blue-green deployment (มี 2 environment สลับกัน): zero downtime แต่ต้นทุนสูง

## มุมมอง Business Owner

- Timeline ที่ประมาณไว้สมจริงไหม? มี buffer (เวลาเผื่อ) ไหม?
- ถ้าต้อง cut scope (ตัดบาง feature ออก) เพื่อให้ทันเวลา → feature ไหนตัดได้?
- มี deliverable (สิ่งที่ส่งมอบ) ระหว่างทางไหม หรือต้องรอจนเสร็จทั้งหมด?
- ต้องสื่อสาร progress (ความคืบหน้า) กับใครบ้าง?
- มี resource constraint (ข้อจำกัดด้านทรัพยากร — คน/เวลา/เงิน) อะไรบ้าง?

## มุมมอง Solution Architect

- การแตก task ตาม component boundaries (ขอบเขตของแต่ละ component) หรือไม่?
- มี integration point (จุดเชื่อมต่อ) ที่ต้อง coordinate (ประสานงาน) กันไหม?
- Test strategy ครอบคลุม critical paths (เส้นทางที่สำคัญ — flow ที่ห้ามพัง) ไหม?
- Deployment strategy เหมาะกับ risk level ของ change ไหม?
- มี performance testing plan (แผนทดสอบประสิทธิภาพ) ไหม (ถ้าจำเป็น)?

## Red Flags — สัญญาณว่ายังไม่ผ่าน Gate นี้

- [ ] Task ใหญ่เกินไป (> 4 ชั่วโมง)
- [ ] ไม่มีลำดับ task
- [ ] ไม่มี milestones
- [ ] ไม่มี definition of done
- [ ] ไม่มี estimate
- [ ] ไม่มี testing strategy
- [ ] ไม่มี deployment strategy

## Output ที่ต้องได้ก่อนไปต่อ

- [ ] Task list พร้อมลำดับ + dependencies
- [ ] Milestones
- [ ] Definition of Done ต่อ task
- [ ] Time estimates
- [ ] Testing strategy
- [ ] Deployment strategy
- [ ] Rollback plan
