# Gate 1 — Business Understanding: ทำความเข้าใจธุรกิจ

## วัตถุประสงค์
ทำให้เข้าใจว่า **ทำไปทำไม** ก่อนที่จะเข้าใจว่า **ทำอย่างไร**
Gate นี้ป้องกันการสร้างสิ่งที่ "ทำงานได้" แต่ "ไม่มีคนใช้" หรือ "ไม่มี business value"

> ปัญหาที่พบบ่อย: โปรแกรมเมอร์โฟกัสที่ "ทำยังไง" โดยข้าม "ทำไปทำไม"
> ผลคือได้ระบบที่ทำงานได้สมบูรณ์ แต่ไม่ได้สร้างคุณค่าให้ธุรกิจ

==================================================

## คำถามที่ต้องถามตัวเอง

### 1. "ทำไปทำไม — Business value คืออะไร?"
- **ทำไมต้องถาม**: ทุกงานต้องสร้างคุณค่าให้ธุรกิจ ถ้าไม่สร้าง → ไม่ควรทำ
- **สิ่งที่ได้**: เหตุผลทางธุรกิจที่ชัดเจน สามารถอธิบายให้คนไม่ใช่โปรแกรมเมอร์เข้าใจ
- **ตัวอย่าง**: "เพิ่มระบบ auto-reorder เพื่อลดเวลาสั่งซื้อจาก 2 ชม. เหลือ 5 นาที = ลดต้นทุนแรงงาน"
- **คำอธิบาย**: Business value (คุณค่าทางธุรกิจ) คือสิ่งที่ธุรกิจได้รับจากการทำงานนี้ เช่น เงินเพิ่มขึ้น ต้นทุนลดลง ลูกค้าพอใจมากขึ้น

### 2. "งานนี้ช่วยอะไร — สร้างรายได้ / ลดต้นทุน / ลดความเสี่ยง / เพิ่มประสิทธิภาพ?"
- **ทำไมต้องถาม**: ช่วยจัด category (หมวดหมู่) ของ value → จัด priority ได้ถูก
- **สิ่งที่ได้**: รู้ว่างานนี้ "ช่วย" แบบไหน → เทียบกับงานอื่นได้
- **ตัวอย่าง**:
  - สร้างรายได้: ทำหน้า e-commerce → ขายของออนไลน์ได้
  - ลดต้นทุน: ทำ automation → ลดเวลาที่ใช้ทำ manual
  - ลดความเสี่ยง: ทำ backup system → ป้องกันข้อมูลหาย
  - เพิ่มประสิทธิภาพ: ทำ dashboard → ตัดสินใจเร็วขึ้น

### 3. "ใครเป็น user — เข้าใจ user journey หรือยัง?"
- **ทำไมต้องถาม**: ถ้าไม่รู้ว่า user ทำอะไร ออกแบบ UX ไม่ได้
- **สิ่งที่ได้**: User journey (เส้นทางผู้ใช้ — ลำดับขั้นตอนที่ผู้ใช้ทำในระบบตั้งแต่ต้นจนจบ) ที่ชัดเจน
- **ตัวอย่าง**: User เปิดแอป → ล็อกอิน → ดูรายการสินค้า → เลือกของใส่ตะกร้า → จ่ายเงิน → ได้ใบเสร็จ

### 4. "Success criteria คืออะไร — วัดได้อย่างไร?"
- **ทำไมต้องถาม**: ถ้าไม่มีเกณฑ์ → ไม่มีทางรู้ว่า "เสร็จ" หรือ "สำเร็จ"
- **สิ่งที่ได้**: เกณฑ์ที่วัดได้ (measurable criteria) → รู้ว่าเมื่อไหร่คือ done
- **คำอธิบาย**: Success criteria (เกณฑ์ความสำเร็จ) คือเงื่อนไขที่ต้องเกิดขึ้นจึงจะถือว่างานสำเร็จ ต้องวัดได้ ไม่ใช่ "ทำให้ดี"
- **ตัวอย่าง**: "user สามารถ checkout ได้ภายใน 3 คลิก" ≠ "ทำหน้า checkout ให้ดี"

### 5. "ลำดับความสำคัญของแต่ละ feature เป็นอย่างไร?"
- **ทำไมต้องถาม**: ถ้าทุกอย่างสำคัญเท่ากัน = ไม่มีอะไรสำคัญ → ทำไม่เสร็จ
- **สิ่งที่ได้**: Priority list ที่ชัดเจน → ทำสิ่งที่สำคัญที่สุดก่อน
- **ตัวอย่าง**: MoSCoW method (Must have / Should have / Could have / Won't have)
  - Must: ล็อกอินได้, ดูสินค้าได้, จ่ายเงินได้
  - Should: ค้นหาสินค้า, filter ราคา
  - Could: wishlist, product comparison
  - Won't: AI recommendation (ทำ phase ถัดไป)

### 6. "มี competitor (คู่แข่ง) หรือ existing solution (ทางออกที่มีอยู่แล้ว) ที่ทำสิ่งนี้อยู่ไหม?"
- **ทำไมต้องถาม**: ถ้ามี → ต้องทำให้ดีกว่า/ต่างจากที่มีอยู่ ถ้าไม่ → อาจเป็น blue ocean (ตลาดที่ยังไม่มีคู่แข่ง) หรืออาจเป็นเพราะไม่มีคนต้องการ
- **สิ่งที่ได้**: ตำแหน่งทางธุรกิจ (market positioning) ที่ชัดเจน
- **ตัวอย่าง**: ทำ project management tool → มี Trello, Asana, Jira อยู่แล้ว → ทำไมต้องทำอีก?

### 7. "Revenue model (โมเดลรายได้) คืออะไร — เก็บเงินอย่างไร?"
- **ทำไมต้องถาม**: ส่งผลต่อ architecture เช่น ต้องมี subscription system, payment gateway, usage tracking
- **สิ่งที่ได้**: ความเข้าใจว่าธุรกิจจะ sustain (ดำรงอยู่ได้) อย่างไร
- **ตัวอย่าง**: Subscription (สมาชิกรายเดือน), Freemium (ฟรีพื้นฐาน เสียเงินเพิ่มเติม), Pay-per-use (จ่ายตามการใช้)

### 8. "Target users (กลุ่มผู้ใช้เป้าหมาย) มีกี่คน — เริ่มต้นกี่คน โตได้ถึงกี่คน?"
- **ทำไมต้องถาม**: กระทบ architecture decision เช่น 100 users ≠ 100,000 users → tech stack ต่างกัน
- **สิ่งที่ได้**: Scale estimate (ประมาณการขนาด) → เลือก tech stack ได้ถูก
- **ตัวอย่าง**: "เริ่ม 50 คน โตได้ 5,000 คนใน 2 ปี" → ออกแบบให้รองรับ 5,000+ ได้

## มุมมอง Business Owner

เจ้าของธุรกิจคิดเรื่อง:
- **ROI (Return on Investment — ผลตอบแทนจากการลงทุน)**: ลงทุนเท่าไหร่ ได้กลับเท่าไหร่
- **Time to Market (เวลาเข้าสู่ตลาด)**: ออกให้เร็วที่สุดที่ยัง "ดีพอ" ได้
- **Opportunity Cost (ต้นทุนค่าเสียโอกาส)**: ถ้าเอาเวลาไปทำงานอื่นจะดีกว่าไหม
- **Customer Impact (ผลกระทบต่อลูกค้า)**: ลูกค้าจะพอใจมากขึ้นหรือไม่
- **Sustainability (ความยั่งยืน)**: ธุรกิจดำรงอยู่ได้ในระยะยาวหรือไม่

## มุมมอง Solution Architect

สถาปนิกระบบคิดเรื่อง:
- **Scalability (ความสามารถในการรองรับขนาดที่โตขึ้น)**: ถ้า user เพิ่ม 10x ระบบรับไหวไหม
- **Maintainability (ความง่ายในการดูแล)**: 1 ปีจากนี้ยังแก้ไขง่ายอยู่ไหม
- **Integration Points (จุดเชื่อมต่อ)**: ต้องเชื่อมกับระบบอื่นอะไรบ้าง
- **Data Model Implications (ผลกระทบต่อโครงสร้างข้อมูล)**: business requirement กระทบ data model อย่างไร
- **Security Requirements (ข้อกำหนดด้านความปลอดภัย)**: ข้อมูลอะไรที่ sensitive (ละเอียดอ่อน) ต้องปกป้อง

## Red Flags — สัญญาณว่ายังไม่ผ่าน Gate นี้

- [ ] ตอบไม่ได้ว่า "ทำไปทำไม"
- [ ] ไม่มี success criteria ที่วัดได้
- [ ] ทุก feature มีความสำคัญเท่ากัน
- [ ] ไม่รู้ว่าใครจะใช้ระบบ
- [ ] ไม่มี user journey
- [ ] ไม่รู้ revenue model
- [ ] ไม่รู้ target scale

## Output ที่ต้องได้ก่อนไปต่อ

- [ ] Business case 3-5 ประโยค
- [ ] User journey ของแต่ละประเภท user
- [ ] Success criteria ที่วัดได้
- [ ] Priority list ของ features
- [ ] Revenue model (ถ้าเป็นโปรเจกต์ใหม่)
- [ ] Target scale estimate
- [ ] Competitor / existing solution analysis
