# Gate 5 — Decision: ตัดสินใจ

## วัตถุประสงค์
เลือก solution จากทางเลือกที่ออกแบบไว้ **พร้อมบันทึกเหตุผล**
Gate นี้ป้องกันการ "เลือกโดยไม่มีเหตุผล" และ "ลืมว่าทำไมเลือกแบบนี้"

> ปัญหาที่พบบ่อย: ตัดสินใจโดย "รู้สึก" ไม่ใช่ "คิด"
> 3 เดือนผ่านไปจำไม่ได้ว่าทำไมเลือกแบบนี้ → ตัดสินใจใหม่ไม่มีข้อมูล

==================================================

## คำถามที่ต้องถามตัวเอง

### 1. "เลือกทางไหน — เพราะอะไร?"
- **ทำไมต้องถาม**: การเลือกที่ดีต้องมี rationale (เหตุผล) ที่ชัดเจน ไม่ใช่ "รู้สึกว่าดี"
- **สิ่งที่ได้**: Decision record (บันทึกการตัดสินใจ) ที่สามารถกลับมาอ้างอิงได้
- **ตัวอย่าง**: "เลือกทาง B เพราะ: 1) ใช้เวลาทำน้อยกว่าทาง C 40%, 2) ความเสี่ยงต่ำกว่า, 3) ทีมมีประสบการณ์กับ tech นี้"

### 2. "ทำไมไม่เลือกทางอื่น?"
- **ทำไมต้องถาม**: เหตุผลที่ไม่เลือก สำคัญเท่ากับเหตุผลที่เลือก → ป้องกันการหยิบทางเก่ามาพิจารณาซ้ำ
- **สิ่งที่ได้**: ความชัดเจนว่าแต่ละทางถูกปฏิเสธเพราะอะไร
- **ตัวอย่าง**: "ไม่เลือกทาง A เพราะไม่ scale ที่ 5,000 users; ไม่เลือกทาง C เพราะใช้เวลา 3 เดือนเกินงบ"

### 3. "ยอมรับความเสี่ยงอะไรบ้าง?"
- **ทำไมต้องถาม**: ทุกการตัดสินใจมีความเสี่ยง ต้องรู้ตัวว่ายอมรับอะไร
- **สิ่งที่ได้**: รายการ accepted risks (ความเสี่ยงที่ยอมรับ) → ไม่เซอร์ไพรส์ทีหลัง
- **ตัวอย่าง**: "ยอมรับว่า: Redis อาจล่มได้ → เตรียม fallback เป็น direct DB query"

### 4. "มีเงื่อนไขอะไรที่ต้องทำก่อน/ระหว่าง/หลัง?"
- **ทำไมต้องถาม**: บางทีเลือก "approve with conditions" (อนุมัติแบบมีเงื่อนไข) → ต้องบันทึกเงื่อนไข
- **สิ่งที่ได้**: รายการ conditions (เงื่อนไข) ที่ต้องทำ
- **ตัวอย่าง**: "อนุมัติ เงื่อนไข: 1) ต้องมี load test ก่อน deploy production, 2) ต้อง feature flag ช่วง 2 สัปดาห์แรก"

### 5. "ถ้าเลือกผิด จะเกิดอะไร — worst case scenario?"
- **ทำไมต้องถาม**: ต้องรู้ว่า worst case (กรณีเลวร้ายที่สุด) เป็นอย่างไร → ถ้ายอมรับได้ → เดินหน้า
- **สิ่งที่ได้**: ความเข้าใจว่าความเสียหายสูงสุดคืออะไร
- **ตัวอย่าง**: "Worst case: ต้อง rewrite (เขียนใหม่) ส่วนนี้ ใช้เวลา 2 สัปดาห์ ไม่กระทบ production"

### 6. "เข้าเกณฑ์ Owner Escalation หรือไม่?"
- **ทำไมต้องถาม**: ถ้าเข้าเกณฑ์แต่ข้าม → ความเสี่ยงที่ไม่ได้รับการตรวจสอบ
- **สิ่งที่ได้**: การยืนยันว่าผ่าน Owner Review Mode แล้ว (ถ้าจำเป็น)
- **ดูเกณฑ์ที่**: MASTER BOOTSTRAP PROMPT.md → OWNER ESCALATION RULE
- **ถ้าเข้าเกณฑ์**: ต้องตอบ 10 คำถามของ Owner Review Mode ก่อนเดินหน้า

### 7. "Decision นี้ reversible (กลับตัวได้) หรือ irreversible (กลับตัวไม่ได้)?"
- **ทำไมต้องถาม**: ถ้า irreversible → ต้อง review ละเอียดกว่า ถ้า reversible → เสี่ยงได้มากกว่า
- **สิ่งที่ได้**: ระดับความระมัดระวังที่เหมาะสม
- **คำอธิบาย**: 
  - Reversible: เลือก UI framework → เปลี่ยนทีหลังได้ (ยากแต่ทำได้)
  - Irreversible: เลือก database schema สำหรับ production ที่มีข้อมูลจริง → เปลี่ยนยากมาก
- **ตัวอย่าง**: Jeff Bezos เรียกว่า "one-way door" (ประตูทางเดียว) vs "two-way door" (ประตูสองทาง)

==================================================

## Owner Review Mode (ถ้าเข้าเกณฑ์ Escalation)

ต้องตอบคำถาม 10 ข้อนี้ก่อนเดินหน้า:

1. ถ้าเป็น CTO จะ approve ไหม?
2. สร้าง business value อะไร?
3. ยอมรับความเสี่ยงอะไร?
4. ความเสี่ยงนี้ acceptable (ยอมรับได้) หรือไม่?
5. Worst case scenario คืออะไร?
6. ถ้าไม่ทำจะเกิดอะไร?
7. มีทางที่ถูกกว่าไหม?
8. มีทางที่ง่ายกว่าไหม?
9. มีทางที่เสี่ยงน้อยกว่าไหม?
10. ROI คุ้มค่ากับ effort ไหม?

หลังตอบครบ → สร้าง Owner Decision Summary:
- Business Impact
- Risk Assessment
- Tradeoff Analysis
- Recommendation (approve / approve with conditions / reject / investigate further)

==================================================

## มุมมอง Business Owner

- การตัดสินใจนี้สร้าง value มากกว่า cost หรือไม่?
- ถ้าผิด เสียเงินเท่าไหร่?
- สามารถเปลี่ยนใจทีหลังได้ไหม?
- การตัดสินใจนี้ปิดโอกาสอะไรในอนาคต?
- ต้องการ approval (การอนุมัติ) จากใครบ้าง?

## มุมมอง Solution Architect

- การตัดสินใจนี้สร้าง technical debt หรือไม่?
- ส่งผลต่อ architecture ในระยะยาวอย่างไร?
- มี migration path (เส้นทางการย้าย) ถ้าต้องเปลี่ยนทีหลังไหม?
- Consistency (ความสอดคล้อง) กับ architecture เดิมเป็นอย่างไร?
- มี precedent (ตัวอย่างก่อนหน้า) ในโปรเจกต์นี้ที่ใช้แนวทางเดียวกันไหม?

==================================================

## Red Flags — สัญญาณว่ายังไม่ผ่าน Gate นี้

- [ ] ตัดสินใจโดยไม่มี rationale เป็นลายลักษณ์อักษร
- [ ] ไม่บันทึกเหตุผลที่ไม่เลือกทางอื่น
- [ ] ไม่ระบุ accepted risks
- [ ] เข้าเกณฑ์ Owner Escalation แต่ไม่ได้ทำ Owner Review
- [ ] ตัดสินใจแบบ "รู้สึก" ไม่ใช่ "คิด"
- [ ] ไม่ได้ประเมินว่า reversible หรือ irreversible

## Output ที่ต้องได้ก่อนไปต่อ

- [ ] Decision record — ใช้ template จาก `templates/decision-registry.md`
- [ ] เหตุผลที่เลือก
- [ ] เหตุผลที่ไม่เลือกทางอื่น
- [ ] Accepted risks
- [ ] Conditions (ถ้ามี)
- [ ] Owner Review Mode completed (ถ้าเข้าเกณฑ์)
- [ ] บันทึกลง Decision Registry
