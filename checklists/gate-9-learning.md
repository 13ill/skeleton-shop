# Gate 9 — Learning & Coaching: เรียนรู้และพัฒนา

## วัตถุประสงค์
สะสมความรู้ ปรับปรุงกระบวนการคิด และวิเคราะห์การทำงานที่ผ่านมาเพื่อพัฒนากลยุทธ์ในการตัดสินใจครั้งถัดไป
Gate นี้ช่วยเปลี่ยน "ประสบการณ์การเขียนโค้ดธรรมดา" ให้กลายเป็น "องค์ความรู้สำหรับพัฒนาทักษะความเป็นเจ้าของระบบ (System Ownership)" และบันทึกบทเรียนเพื่อหลีกเลี่ยงความผิดพลาดซ้ำเดิม

> ปัญหาที่พบบ่อย: เมื่องานเสร็จ ทุกคนมุ่งหน้าทำงานชิ้นต่อไปทันทีโดยไม่ได้สรุปบทเรียน
> ผลคือเกิดข้อผิดพลาดเดิมซ้ำๆ, ทักษะของนักพัฒนาไม่ได้รับการอัพเกรด และไม่มีการจัดการความรู้ในองค์กร

==================================================

## คำถามเพื่อการทบทวนตัวเอง (Retrospective Questions)

### 1. "อะไรคืองานที่ทำได้ดี และอะไรที่น่าจะทำได้ดีกว่านี้?"
- **ทำไมต้องถาม**: เพื่อระบุจุดแข็งที่ควรทำต่อไป (maintain) และจุดอ่อนที่ต้องปรับปรุง (improvement)
- **สิ่งที่ได้**: ความเข้าใจในประสิทธิภาพและศักยภาพของตัวเอง
- **ตัวอย่าง**: "ออกแบบระบบฐานข้อมูลได้คล่องตัวดี แต่ใช้เวลาเขียน test นานเกินไปเนื่องจากขาดการ mock ข้อมูลที่ดี"

### 2. "เราเจอ Blind Spot (จุดอับสายตา) อะไรบ้างในงานนี้?"
- **ทำไมต้องถาม**: จุดอับสายตาคือสิ่งที่เราไม่รู้ว่าเราไม่รู้ (unknown unknowns) การมองเห็นมันในภายหลังจะช่วยป้องกันความประมาทในงานหน้า
- **สิ่งที่ได้**: การพัฒนาสติและมุมมองที่รอบคอบขึ้น
- **ตัวอย่าง**: "ลืมไปว่าลูกค้าบางกลุ่มใช้ Web Browser เวอร์ชันเก่ามาก ทำให้ฟีเจอร์ JavaScript สมัยใหม่ที่ใช้ไม่ทำงาน"

### 3. "ระยะเวลาและทรัพยากรที่ใช้จริง แตกต่างจากที่ประเมินไว้ (Estimate Variance) อย่างไร?"
- **ทำไมต้องถาม**: เพื่อปรับปรุงทักษะการประเมินเวลา (Estimation) ซึ่งเป็นสิ่งสำคัญสำหรับผู้นำทีมและเจ้าของธุรกิจ
- **สิ่งที่ได้**: ความแม่นยำในการวางแผนงานถัดไปและลดความน่าจะเป็นที่จะส่งงานเลท
- **วิธีวิเคราะห์**:
  - หากใช้เวลาน้อยกว่าคาด → เราคาดการณ์เผื่อเกินไป หรือเจอปัจจัยบวกอะไร?
  - หากใช้เวลามากกว่าคาด → ติดขัดที่จุดใด? (เช่น เจอปัญหาเทคนิคที่คาดไม่ถึง, ขอบเขตงานเปลี่ยนกลางคัน)

### 4. "เราได้สร้าง Technical Debt (หนี้ทางเทคนิค) เพิ่มเติมในงานนี้หรือไม่?"
- **ทำไมต้องถาม**: หากปล่อยให้หนี้พอกพูนโดยไม่มีการลงบันทึก ระบบจะช้าลงและบำรุงรักษาได้ยากขึ้นเรื่อยๆ
- **สิ่งที่ได้**: บัญชีหนี้ทางเทคนิคที่โปร่งใสและวางแผนจ่ายคืนได้ (refactoring planning)
- **การจัดการ**: บันทึกลงใน Learning/Technical Debt Registry พร้อมเสนอเวลาที่จะเข้ามาแก้ไข

### 5. "ฟีเจอร์นี้สร้าง Business Value (คุณค่าทางธุรกิจ) ได้ตรงตามเป้าหมายของ Gate 1 หรือไม่?"
- **ทำไมต้องถาม**: เพื่อประเมินว่าการตัดสินใจทางสถาปัตยกรรมและการลงทุนแรงงานของเราให้ผลตอบแทนที่คุ้มค่า (ROI) แก่ธุรกิจหรือไม่
- **สิ่งที่ได้**: การคิดเชิงธุรกิจที่แหลมคมยิ่งขึ้นของผู้ออกแบบระบบ

## การประเมินทักษะและจุดที่ต้องพัฒนา (Skill Gap Assessment)

วิเคราะห์และบันทึกทักษะที่เกี่ยวข้อง:

- **Technical Skills (ทักษะเชิงเทคนิค)**: ต้องการศึกษาเรื่องใดเพิ่มเติมเพื่อให้ทำงานประเภทนี้ได้เร็วและมีคุณภาพสูงขึ้นในครั้งหน้า? (เช่น การเขียน Regex, การตั้งค่า Docker, การออกแบบดัชนีฐานข้อมูล)
- **Conceptual/Architecture Skills (ทักษะเชิงสถาปัตยกรรม)**: กระบวนการคิดเชิงระบบและสถาปัตยกรรมยังติดขัดที่ตรงไหน? (เช่น การเลือกใช้ออบเจกต์เชื่อมโยง, การกระจายโหลดของข้อมูล)
- **Business/Product Thinking (ทักษะความคิดเชิงผลิตภัณฑ์และธุรกิจ)**: เราเข้าใจความต้องการของลูกค้าและโมเดลธุรกิจลึกซึ้งพอหรือยัง?

## กิจกรรมหลังปิดการทำงาน (Post-Task Protocol)

ดำเนินการดังต่อไปนี้เป็นขั้นตอนสุดท้ายของ Task เสมอ:

1. **Update Learning Registry**: บันทึกสรุปบทเรียนและข้อควรระวังลงใน `learning-registry.md` ของโปรเจกต์
2. **Review Skill Gaps**: หากพบจุดขาดแคลนความรู้ที่สำคัญ ให้จดเป็นรายการเรียนรู้ (learning goals) ไว้พัฒนาตนเอง
3. **Coaching Session**: หากทำงานกับ AI ใน Coaching Mode ให้ AI สรุปมุมมองและการคิดแบบ CTO เกี่ยวกับการออกแบบและการลงมือทำใน Task นี้เพื่อยกระดับทักษะ

## Red Flags — สัญญาณของการไม่ยอมเรียนรู้

- [ ] ปิด Task โดยไม่มีการกรอกข้อมูลใน Learning Registry
- [ ] ระบุว่า "ไม่มีอะไรต้องปรับปรุง" หรือ "ทุกอย่างสมบูรณ์แบบร้อยเปอร์เซ็นต์"
- [ ] เกิดปัญหาระบบล่มหรือพังแบบเดิมกับงานที่แล้ว แต่ไม่มีการทบทวนหาสาเหตุรากเหง้า (Root Cause Analysis)
- [ ] ประเมินเวลาคลาดเคลื่อนมากกว่า 100% แต่คิดว่าการประเมินเวลานั้นถูกต้องแล้ว

## Output ที่ต้องได้ใน Gate นี้

- [ ] บันทึกการสรุปบทเรียนใน **Learning Registry** (เช่น `learning-registry.md`)
- [ ] รายการทักษะที่ต้องฝึกฝนเพิ่มเติม (Skill Gap Log)
- [ ] ข้อเสนอแนะสำหรับปรับปรุงกระบวนการพัฒนา (Process Improvements) สำหรับ Task ถัดไป
