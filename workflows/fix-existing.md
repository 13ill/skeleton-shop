# คู่มือ: แก้ไข / ปรับปรุงโปรเจกต์เก่า

คู่มือนี้เป็นขั้นตอนการทำงานสำหรับ **รับ task มาแก้ไขหรือปรับปรุงโปรเจกต์ที่มีอยู่แล้ว**
ทุกขั้นตอนผูกกับ Gate System — ห้ามข้ามด่านจนกว่าจะผ่านครบ

> ⚠️ สิ่งที่ต่างจากโปรเจกต์ใหม่: ต้อง **ทำความเข้าใจระบบเดิมก่อน** ไม่ใช่แค่เข้าใจ task

==================================================

## ภาพรวมขั้นตอน

```
ขั้นที่ 1: รับ task + ทำความเข้าใจ context (Gate 0)
    ↓
ขั้นที่ 2: เข้าใจว่าทำไมต้องแก้ — business context (Gate 1)
    ↓
ขั้นที่ 3: เข้าใจระบบเดิม — architecture ปัจจุบัน (Gate 2)
    ↓
ขั้นที่ 4: วิเคราะห์ผลกระทบ + ความเสี่ยง (Gate 3)
    ↓
ขั้นที่ 5: ออกแบบการแก้ไข (Gate 4)
    ↓
ขั้นที่ 6: ตัดสินใจ (Gate 5)
    ↓
ขั้นที่ 7: วางแผนการแก้ไข (Gate 6)
    ↓
ขั้นที่ 8: ลงมือแก้ (Gate 7)
    ↓
ขั้นที่ 9: Review + ตรวจ architecture (Gate 8 + 8.5)
    ↓
ขั้นที่ 10: เรียนรู้ (Gate 9)
```

==================================================

## ขั้นที่ 1: รับ task + ทำความเข้าใจ context → Gate 0

### สิ่งที่ต้องทำ
1. อ่าน task แล้วเขียนสรุปด้วยภาษาตัวเอง
2. ระบุว่า: แก้ bug / เพิ่ม feature / refactor (ปรับโครงสร้างโค้ดโดยไม่เปลี่ยนพฤติกรรม) / performance (ปรับประสิทธิภาพ)
3. ระบุว่างานนี้ urgent (เร่งด่วน) แค่ไหน — จริงๆ urgent หรือแค่รู้สึก urgent
4. ระบุ scope (ขอบเขต) — แก้ตรงไหน ไม่แก้ตรงไหน
5. ตรวจสอบว่ามีข้อมูล context เพียงพอหรือยัง

### Output ที่ต้องได้
- สรุป task 1-3 ประโยค
- ประเภทงาน (bug fix / feature / refactor / performance)
- ระดับความเร่งด่วน + เหตุผล
- ขอบเขตงาน
- รายการคำถามที่ยังไม่มีคำตอบ

### ⚠️ Red Flags
- "แก้ด่วน" โดยไม่มี context → อาจแก้ผิดที่
- ไม่รู้ว่าระบบเดิมทำงานอย่างไร → อันตราย
- ขอบเขตไม่ชัด → scope creep (งานบานปลาย — เริ่มจากแก้นิดเดียวกลายเป็นแก้ทั้งระบบ)

→ ดู checklist เพิ่มเติม: `checklists/gate-0-task-intake.md`

==================================================

## ขั้นที่ 2: เข้าใจว่าทำไมต้องแก้ → Gate 1

### สิ่งที่ต้องทำ
1. ตอบว่า "ถ้าไม่แก้จะเกิดอะไรขึ้น?" (impact of doing nothing)
2. ระบุว่าใครได้รับผลกระทบ — user / ทีม / ธุรกิจ
3. ระบุ priority (ลำดับความสำคัญ) เทียบกับงานอื่นที่ค้างอยู่
4. ระบุว่าสิ่งนี้เกิดขึ้นเพราะอะไร — root cause (สาเหตุรากฐาน — ปัญหาจริงๆ ไม่ใช่แค่อาการ) ถ้าเป็น bug

### Output ที่ต้องได้
- Business justification (เหตุผลทางธุรกิจ) ว่าทำไมต้องแก้
- ผลกระทบถ้าไม่แก้
- Priority เทียบกับงานอื่น
- Root cause analysis (ถ้าเป็น bug)

### ⚠️ Red Flags
- ไม่รู้ว่าถ้าไม่แก้จะเกิดอะไร → อาจไม่จำเป็นต้องแก้ตอนนี้
- แก้อาการไม่ได้แก้สาเหตุ → จะเจอปัญหาเดิมซ้ำ
- Priority สูงทุกงาน → ไม่มีงานไหนเป็น priority จริง

→ ดู checklist เพิ่มเติม: `checklists/gate-1-business.md`

==================================================

## ขั้นที่ 3: เข้าใจระบบเดิม → Gate 2

### สิ่งที่ต้องทำ (สำคัญมากสำหรับโปรเจกต์เก่า)
1. โหลด architecture index ของโปรเจกต์ (ถ้ามี)
2. ระบุ module (ส่วนย่อย) ที่เกี่ยวข้องกับ task นี้
3. เข้าใจ data flow (การไหลของข้อมูล) ในส่วนที่จะแก้
4. ระบุ dependencies (สิ่งที่พึ่งพา) — ส่วนนี้เชื่อมกับอะไรบ้าง
5. ตรวจสอบว่ามี tests เดิมหรือไม่ — ครอบคลุมส่วนที่จะแก้หรือเปล่า
6. ดู code history (ประวัติการแก้ไข) — เคยแก้ส่วนนี้มาก่อนหรือยัง

### Output ที่ต้องได้
- แผนที่ modules ที่เกี่ยวข้อง
- Data flow ของส่วนที่จะแก้
- รายชื่อ dependencies
- สถานะ test coverage (ความครอบคลุมของการทดสอบ)
- ประวัติการแก้ไขที่เกี่ยวข้อง

### ⚠️ Red Flags
- ไม่อ่านโค้ดเดิมก่อนแก้ → อาจทำลายสิ่งที่มีอยู่
- ไม่ตรวจ dependencies → แก้ตรงนี้แต่พังตรงอื่น
- ไม่มี tests → แก้แล้วไม่มีทางรู้ว่าพังอะไรหรือเปล่า
- เคยแก้ส่วนนี้หลายรอบแล้ว → อาจเป็นปัญหาเชิงสถาปัตยกรรมที่ต้องแก้ root cause

→ ดู checklist เพิ่มเติม: `checklists/gate-2-system.md`

==================================================

## ขั้นที่ 4: วิเคราะห์ผลกระทบ + ความเสี่ยง → Gate 3

### สิ่งที่ต้องทำ
1. ทำ impact analysis (วิเคราะห์ผลกระทบ):
   - ส่วนไหนของระบบจะได้รับผลกระทบ
   - user กี่คนที่จะได้รับผลกระทบ
   - มี downstream systems (ระบบที่อยู่ถัดไป) ที่ได้รับผลหรือไม่
2. ระบุความเสี่ยงของการแก้ไข:
   - อาจพังอะไรได้บ้าง
   - rollback plan (แผนย้อนกลับ — ถ้าแก้แล้วพังจะกลับไปสถานะเดิมอย่างไร)
   - downtime (ระบบหยุดทำงาน) ที่อาจเกิดขึ้น
3. ตรวจสอบว่าเข้าเกณฑ์ Owner Escalation หรือไม่

### Output ที่ต้องได้
- Impact analysis document
- Risk register สำหรับ task นี้
- Rollback plan
- Owner Escalation: ใช่/ไม่ใช่ + เหตุผล

### ⚠️ Red Flags
- "แก้นิดเดียวไม่น่ามีปัญหา" → ทุกการเปลี่ยนแปลงมีความเสี่ยง
- ไม่มี rollback plan → ถ้าพังจะทำอย่างไร
- กระทบ payment/auth/data แต่ไม่ escalate → ละเลยกฎ Owner Escalation

→ ดู checklist เพิ่มเติม: `checklists/gate-3-risk.md`

==================================================

## ขั้นที่ 5: ออกแบบการแก้ไข → Gate 4

### สิ่งที่ต้องทำ
1. ออกแบบทางเลือกอย่างน้อย 2 ทาง:
   - Quick fix (แก้เร็ว ทำงานได้ แต่อาจเป็น technical debt — หนี้ทางเทคนิค ที่ต้องกลับมาแก้ทีหลัง)
   - Proper fix (แก้ถูกต้อง อาจใช้เวลามากกว่า)
   - Refactor (ปรับโครงสร้าง แก้ root cause)
2. วิเคราะห์ tradeoff ของแต่ละทาง
3. ตรวจสอบว่าการแก้ไข backward compatible (ทำงานร่วมกับของเดิมได้) หรือไม่
4. ระบุว่าต้องแก้ data/schema หรือไม่

### Output ที่ต้องได้
- ทางเลือกอย่างน้อย 2 ทาง + tradeoff
- Backward compatibility analysis
- Data/schema change assessment
- ทางเลือกที่แนะนำ + เหตุผล

### ⚠️ Red Flags
- มีทางเดียว → ไม่ได้คิดทางอื่น
- เลือก quick fix เสมอ → สะสม technical debt
- เลือก refactor ทุกครั้ง → อาจ over-engineer (ออกแบบเกินจำเป็น)
- ต้องแก้ schema แต่ไม่มี migration plan (แผนการย้ายข้อมูล) → อันตรายมาก

→ ดู checklist เพิ่มเติม: `checklists/gate-4-design.md`

==================================================

## ขั้นที่ 6: ตัดสินใจ → Gate 5

### สิ่งที่ต้องทำ
1. เลือกทางจากขั้นที่ 5
2. บันทึก rationale (เหตุผล)
3. ถ้าเข้า Owner Escalation → ผ่าน Owner Review Mode ก่อน
4. บันทึกลง Decision Registry

→ ดู checklist เพิ่มเติม: `checklists/gate-5-decision.md`

==================================================

## ขั้นที่ 7: วางแผนการแก้ไข → Gate 6

### สิ่งที่ต้องทำ
1. แตก task เป็นขั้นตอนย่อย
2. ระบุลำดับ — อะไรต้องทำก่อน
3. ระบุ checkpoint (จุดตรวจสอบ) ระหว่างทาง
4. ระบุ testing strategy (กลยุทธ์การทดสอบ):
   - เขียน test ใหม่หรือแก้ test เดิม
   - manual testing (ทดสอบด้วยมือ) ต้องทำอะไรบ้าง
5. ระบุ deployment strategy (กลยุทธ์การ deploy):
   - deploy ทีเดียว / deploy ทีละส่วน (progressive rollout)
   - feature flag (สวิตช์เปิด-ปิด feature — เปิดให้ user บางกลุ่มก่อน) ต้องใช้หรือไม่

### Output ที่ต้องได้
- Task list พร้อมลำดับ
- Testing plan
- Deployment plan
- Rollback plan (ถ้ายังไม่มี)

→ ดู checklist เพิ่มเติม: `checklists/gate-6-planning.md`

==================================================

## ขั้นที่ 8: ลงมือแก้ → Gate 7

### สิ่งที่ต้องทำ
1. ทำตาม task list
2. ตรวจสอบที่ checkpoint แต่ละจุด
3. รัน tests เดิมเพื่อดูว่าไม่ทำลายอะไร (regression testing — การทดสอบถดถอย)
4. เขียน/แก้ tests ใหม่ตามแผน
5. ถ้าพบปัญหาที่ไม่ได้คาดไว้ → หยุด แล้วกลับไป Gate 3 หรือ 4

### ⚠️ Red Flags เฉพาะโปรเจกต์เก่า
- แก้ไป test พัง → ต้องหยุดวิเคราะห์ก่อนดันทุรัง
- ต้อง "hack" หรือ "workaround" เพื่อให้ทำงานได้ → สัญญาณว่าออกแบบไม่ดี
- แก้ไฟล์เดียวกันหลายครั้งในรอบเดียว → อาจต้อง refactor แทน

→ ดู checklist เพิ่มเติม: `checklists/gate-7-execution.md`

==================================================

## ขั้นที่ 9: Review → Gate 8 + Gate 8.5

### Gate 8 - Review
1. ตรวจว่าแก้ตรงตาม requirements
2. Tests ผ่านทั้งหมด (ทั้ง test ใหม่และ test เดิม)
3. Code quality ดี — อ่านง่าย, มี comments, ตาม convention
4. Security check — ไม่สร้างช่องโหว่ใหม่

### Gate 8.5 - Architecture Change Review
1. มีอะไรเปลี่ยนจาก architecture เดิมหรือไม่
2. ถ้าเปลี่ยน → อัพเดท architecture docs
3. อัพเดท module map, dependency map ถ้าจำเป็น

→ ดู checklist เพิ่มเติม: `checklists/gate-8-review.md` และ `checklists/gate-8.5-arch-review.md`

==================================================

## ขั้นที่ 10: เรียนรู้ → Gate 9

### สิ่งที่ต้องทำ (สำคัญเป็นพิเศษสำหรับโปรเจกต์เก่า)
1. สรุปว่าเรียนรู้อะไร
2. ถ้าเป็น bug: ทำไมถึงเกิด? ป้องกันได้อย่างไรในอนาคต?
3. ถ้าเป็น feature: มีอะไรในระบบเดิมที่เซอร์ไพรส์เราหรือไม่?
4. ระบบเดิมมีจุดไหนที่ควรปรับปรุง (สังเกตระหว่างแก้)
5. บันทึกลง Learning Registry

### คำถามสำหรับ reflection (การทบทวน)
- ถ้าทำใหม่จะทำต่างไหม?
- มี pattern (รูปแบบ) อะไรที่เห็นซ้ำๆ ในโปรเจกต์นี้?
- มี skill (ทักษะ) อะไรที่ขาดและต้องพัฒนา?

→ ดู checklist เพิ่มเติม: `checklists/gate-9-learning.md`
