# Gate 8.5 — Architecture Change Review: ทบทวนการปรับปรุงสถาปัตยกรรม

## วัตถุประสงค์
ตรวจสอบผลกระทบเชิงลึกเมื่อมีการแก้ไขโครงสร้าง **สถาปัตยกรรมระบบ (Architecture)** หรือ **ฐานข้อมูล (Database Schema)** หรือ **API Contracts (ข้อตกลงในการแลกเปลี่ยนข้อมูล)**
Gate นี้เป็นด่านคัดกรองพิเศษ (Escalation Gate) เพื่อป้องกันภัยพิบัติระดับระบบ (System-wide Failures) เช่น ข้อมูลสูญหาย ระบบล่มแบบเฉียบพลัน หรือ API ปลายทางทำงานไม่ได้เนื่องจากการแก้ไขแบบย้อนหลังไม่เข้ากัน (breaking changes)

> ปัญหาที่พบบ่อย: แก้ฐานข้อมูลหรือแก้โครงสร้างโฟลเดอร์ใหม่ แล้วคิดว่าระบบทำงานปกติบนเครื่องตัวเอง
> แต่พอนำขึ้นระบบจริง (production) กลับทำให้ฟังก์ชันอื่นล่ม ข้อมูลพัง หรือเกิดคอขวดประสิทธิภาพการทำงาน

==================================================

## หัวข้อการตรวจสอบระดับสถาปัตยกรรม (Architectural Checks)

### 1. Database Schema Changes & Migration (การเปลี่ยนแปลงฐานข้อมูลและการย้ายข้อมูล)
- **คำถาม**: การเพิ่ม/ลด/เปลี่ยนประเภทฟิลด์ในฐานข้อมูล จะส่งผลกระทบต่อระบบที่กำลังรันอยู่หรือไม่?
- **ทำไมต้องถาม**: การรัน migration บนฐานข้อมูลที่มีข้อมูลขนาดใหญ่อาจทำให้ตารางล็อก (table locking) ส่งผลให้ระบบหยุดทำงาน หรือข้อมูลเดิมสูญหาย
- **ข้อตรวจสอบ**:
  - [ ] มีสคริปต์สำหรับการย้ายข้อมูลย้อนกลับ (Rollback script/down migration) หรือไม่?
  - [ ] การเปลี่ยนชื่อฟิลด์หรือตารางทำแบบสองขั้นตอน (two-phase commit — เพิ่มฟิลด์ใหม่ก่อน แล้วย้ายข้อมูล จากนั้นจึงลบฟิลด์เก่า) เพื่อไม่ให้ระบบเดิมพังระหว่าง deploy หรือไม่?
  - [ ] มีการทำดัชนี (indexes) เพิ่มเติมสำหรับ query ใหม่เพื่อป้องกันการดึงข้อมูลช้า (slow query) หรือไม่?

### 2. Backward Compatibility (การรองรับการทำงานร่วมกับระบบเวอร์ชันเก่า)
- **คำถาม**: โค้ดหรือ API ที่ปรับปรุงใหม่นี้ ยังรองรับระบบเดิม หรือ Client ที่ไม่ได้อัพเดท (เช่น Mobile App หรือบริการอื่นๆ) หรือไม่?
- **ทำไมต้องถาม**: หากฝั่ง Server แก้ API format กระทันหัน Mobile App ของลูกค้าที่ยังไม่ได้กดอัปเดตจะใช้งานไม่ได้ทันที
- **ข้อตรวจสอบ**:
  - [ ] API ที่แก้ไม่มี breaking changes (เช่น การเปลี่ยนชื่อคีย์ หรือย้ายตำแหน่งของฟิลด์ใน JSON payload)
  - [ ] หากจำเป็นต้องเปลี่ยนโครงสร้าง มีการสร้างเวอร์ชันใหม่ของ API (เช่น `/api/v2/` แทนที่จะเขียนทับ `/api/v1/`) หรือไม่?
  - [ ] โครงสร้างข้อมูลในคิว (Event payload/Message queues) ยังสามารถอ่านและประมวลผลโดย consumer ตัวเดิมได้หรือไม่?

### 3. Downstream & Dependency Impact (ผลกระทบต่อระบบที่พึ่งพาข้อมูล)
- **คำถาม**: การเปลี่ยนแปลงนี้ทำให้ระบบอื่น (internal/external services) ที่เชื่อมต่อกับระบบเรา ต้องแก้ไขตามหรือไม่?
- **ทำไมต้องถาม**: ระบบซอฟต์แวร์สมัยใหม่มักเชื่อมต่อกันเป็นทอดๆ การเปลี่ยนแปลงที่จุดหนึ่งอาจก่อให้เกิดผลกระทบโดมิโน (domino effect)
- **ข้อตรวจสอบ**:
  - [ ] ได้แจ้งและทำความเข้าใจกับทีมผู้ดูแลระบบปลายทาง (downstream systems) เกี่ยวกับการเปลี่ยนแปลงนี้แล้ว
  - [ ] มีระบบป้องกันภัยเมื่อระบบอื่นล่ม (circuit breaker หรือ fallback logic) เพื่อไม่ให้ระบบของเราล่มตามไปด้วย

### 4. Operational Cost & Infrastructure Impact (ค่าใช้จ่ายเชิงระบบและโครงสร้างพื้นฐาน)
- **คำถาม**: การออกแบบใหม่นี้จะเพิ่มภาระให้เครื่องเซิร์ฟเวอร์ หรือทำให้ค่าใช้จ่ายคลาวด์ (Cloud spending) สูงขึ้นอย่างรวดเร็วหรือไม่?
- **ทำไมต้องถาม**: การเขียน query ที่ดึงข้อมูลบ่อยเกินไป หรือการใช้ CPU/Memory หนักๆ จะส่งผลต่อค่าใช้จ่ายรายเดือนของบริษัทโดยตรง
- **ข้อตรวจสอบ**:
  - [ ] ออกแบบระบบให้ใช้การเก็บข้อมูลชั่วคราว (caching) ในจุดที่เหมาะสม
  - [ ] ประเมินปริมาณทรัพยากร (CPU, RAM, Database connections) ที่ต้องใช้งานในเวลาที่มีผู้ใช้งานหนาแน่น (peak hours)

## แผนเผชิญเหตุและการกู้คืน (Rollback & Recovery Plan)

เมื่อปรับปรุงสถาปัตยกรรมระดับใหญ่ ต้องเตรียมแผนเผชิญเหตุเสมอ:

1. **How to Rollback? (จะย้อนกลับอย่างไร?)**
   - หากขึ้นระบบแล้วพัง จะสั่งย้อนโค้ดกลับไปเวอร์ชันเดิมได้อย่างไรโดยใช้เวลาน้อยที่สุด? (เช่น Blue-Green deployment หรือ Feature Flags)
2. **Data Safety (ความปลอดภัยของข้อมูล)**
   - หากย้อนเวอร์ชันโค้ดกลับไป ข้อมูลใหม่ที่ลูกค้ากรอกมาในระหว่างที่ระบบเกิดปัญหานั้น จะถูกย้ายกลับมาหรือเก็บรักษาไว้อย่างไรโดยไม่สูญหาย?
3. **Downtime Estimate (การประมาณการหยุดทำงานของระบบ)**
   - การอัปเดตนี้จำเป็นต้องปิดระบบเพื่อทำการซ่อมบำรุง (scheduled maintenance) หรือไม่? ถ้าต้องทำ จะเลือกช่วงเวลาใดที่ส่งผลกระทบต่อลูกค้าน้อยที่สุด?

## Red Flags — สัญญาณความเสี่ยงสูงระดับสถาปัตยกรรม

- [ ] การเปลี่ยน Database Schema ไม่มี rollback plan หรือ scripts
- [ ] มี breaking changes ใน API ที่ไม่มีการจัดการ versioning
- [ ] มีจุดเสี่ยงที่จะทำให้เกิด "Single Point of Failure" (จุดเดียวพัง ล่มทั้งระบบ)
- [ ] ไม่มีระบบ logging หรือ monitoring ที่คอยจับตาดูจุดที่มีการแก้ไขสถาปัตยกรรม
- [ ] ใช้วิธีเปลี่ยนสถาปัตยกรรมเพื่อแก้ปัญหาระยะสั้น (short-term hack) ที่ทำให้โครงสร้างหลักของระบบบิดเบี้ยว

## Output ที่ต้องบันทึกและส่งมอบก่อนปิดงาน

- [ ] **Architecture Impact Assessment Summary** (บทสรุปการประเมินผลกระทบสถาปัตยกรรม) บันทึกรายละเอียดการเปลี่ยนแปลงเชิงโครงสร้าง
- [ ] **Database Migration Plan** (แผนการย้ายข้อมูล) และบททดสอบความเร็วในการรัน migration
- [ ] **Rollback Checklist** (รายการขั้นตอนการย้อนคืนระบบ) หากเกิดความผิดพลาดในระบบจริง
- [ ] บันทึกเหตุผลการเปลี่ยนแปลงลงใน **Decision Registry** พร้อมระบุข้อดี/ข้อเสีย และทางเลือกอื่นที่ถูกปัดตกไป
