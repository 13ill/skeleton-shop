# Gate 3 — Risk Discovery: ค้นหาความเสี่ยง

## วัตถุประสงค์
ค้นหา **ทุกสิ่งที่อาจผิดพลาด** ก่อนลงมือทำ
Gate นี้ป้องกันการ "เจอปัญหาตอนทำ" ด้วยการ "หาปัญหาก่อนเริ่ม"

> ปัญหาที่พบบ่อย: คิดว่า "ไม่น่ามีปัญหา" แล้วเจอปัญหาตอนทำไปแล้วครึ่งทาง
> ต้นทุนการแก้ปัญหาเพิ่มขึ้นแบบ exponential (เพิ่มแบบทวีคูณ) ตามเวลาที่ผ่านไป

## คำถามที่ต้องถามตัวเอง

### 1. "อะไรอาจทำไม่ได้ — มี technical risk (ความเสี่ยงทางเทคนิค) อะไรบ้าง?"
- **ทำไมต้องถาม**: บาง feature อาจยากกว่าที่คิด หรืออาจทำไม่ได้ด้วย tech stack ที่เลือก
- **สิ่งที่ได้**: รายการ technical risks ที่ต้องจัดการ
- **ตัวอย่าง**: 
  - Real-time sync (การซิงค์ข้อมูลแบบทันที) ข้าม devices อาจซับซ้อนกว่าที่คิด
  - ต้อง process รูปภาพ 10,000 รูปต่อวัน → ต้องมี background job (งานที่ทำอยู่เบื้องหลัง)

### 2. "อะไรอาจทำแล้วไม่มีคนใช้ — มี business risk (ความเสี่ยงทางธุรกิจ) อะไรบ้าง?"
- **ทำไมต้องถาม**: ทำสิ่งที่ไม่มีคนใช้ = เสียเวลาและเงิน
- **สิ่งที่ได้**: การประเมินว่า feature ใดมีความเสี่ยงที่จะไม่มีคนใช้
- **ตัวอย่าง**: 
  - สร้าง feature ที่ลูกค้าไม่เคยขอ → market risk (ความเสี่ยงทางตลาด)
  - ตั้งราคาผิด → pricing risk (ความเสี่ยงด้านราคา)

### 3. "อะไรอาจทำให้ระบบล่ม — มี operational risk (ความเสี่ยงด้านการดำเนินงาน) อะไรบ้าง?"
- **ทำไมต้องถาม**: ระบบที่ล่มบ่อย = ลูกค้าหาย = รายได้หาย
- **สิ่งที่ได้**: จุดที่ต้องเสริมความแข็งแกร่ง
- **ตัวอย่าง**: 
  - ถ้า database เต็ม → ระบบหยุดทำงาน
  - ถ้า third-party API (API ของบริการภายนอก) ล่ม → feature ที่พึ่งพาก็ใช้ไม่ได้
  - ถ้า traffic spike (ปริมาณ request พุ่งขึ้นกะทันหัน) → ระบบรับไม่ไหว

### 4. "มี single point of failure ตรงไหนบ้าง?"
- **ทำไมต้องถาม**: ถ้ามีจุดเดียวที่พังแล้วพังทั้งระบบ → ต้องแก้ก่อน
- **สิ่งที่ได้**: รายการจุดที่ต้องเพิ่ม redundancy (ระบบสำรอง)
- **คำอธิบาย**: Single point of failure (SPOF — จุดล้มเหลวจุดเดียว) คือจุดที่ถ้ามันพังจะทำให้ทั้งระบบพังตาม ไม่มีทางเลี่ยง
- **ตัวอย่าง**: มี database server เดียว → ถ้าเครื่องนี้ล่ม ทุกอย่างหยุด

### 5. "ถ้าเกิดปัญหา จะ rollback (ย้อนกลับ) อย่างไร?"
- **ทำไมต้องถาม**: ถ้าไม่มีแผน rollback แล้วเกิดปัญหา → จะยิ่งพัง
- **สิ่งที่ได้**: Rollback plan (แผนย้อนกลับ — วิธีกลับไปสถานะก่อนหน้าถ้าสิ่งที่ deploy ไปมีปัญหา)
- **ตัวอย่าง**: 
  - Database migration → ต้องมี down migration (การย้อน migration กลับ) ด้วย
  - Feature ใหม่ → ใช้ feature flag (สวิตช์เปิด-ปิด) เพื่อปิดได้ทันที

### 6. "Security risk (ความเสี่ยงด้านความปลอดภัย) มีอะไรบ้าง?"
- **ทำไมต้องถาม**: ข้อมูลรั่ว / ถูก hack → ความเสียหายทั้งทางธุรกิจและทางกฎหมาย
- **สิ่งที่ได้**: รายการ security risks + มาตรการป้องกัน
- **ตัวอย่าง**:
  - เก็บ password แบบ plain text (ข้อความธรรมดา) → ต้อง hash (เข้ารหัสทางเดียว)
  - ไม่มี rate limiting (จำกัดจำนวน request) → โดน brute force (ลองรหัสผ่านเรื่อยๆ จนเจอ)
  - SQL injection (การแทรกคำสั่ง SQL) → ต้อง parameterize queries (ใช้ตัวแปรแทนการต่อ string)

### 7. "มี data risk (ความเสี่ยงด้านข้อมูล) อะไรบ้าง?"
- **ทำไมต้องถาม**: ข้อมูลหาย / เสียหาย / ไม่สอดคล้อง = ปัญหาใหญ่ที่แก้ยาก
- **สิ่งที่ได้**: แผนปกป้องข้อมูล
- **ตัวอย่าง**:
  - ไม่มี backup → ข้อมูลหายแล้วกู้ไม่ได้
  - ไม่มี data validation (การตรวจสอบข้อมูล) → ข้อมูลเสียหายเข้า database
  - Concurrent updates (แก้ข้อมูลพร้อมกัน) → data inconsistency (ข้อมูลไม่ตรงกัน)

### 8. "มี compliance risk (ความเสี่ยงด้านการปฏิบัติตามกฎหมาย) อะไรบ้าง?"
- **ทำไมต้องถาม**: ละเมิดกฎหมาย → ค่าปรับ + ความเสียหายต่อชื่อเสียง
- **สิ่งที่ได้**: รายการกฎหมาย/ข้อบังคับที่เกี่ยวข้อง
- **ตัวอย่าง**: PDPA (พ.ร.บ. คุ้มครองข้อมูลส่วนบุคคล), GDPR (กฎหมายคุ้มครองข้อมูลของ EU), PCI-DSS (มาตรฐานความปลอดภัยสำหรับ payment)

### 9. "มี dependency risk (ความเสี่ยงจากการพึ่งพา) อะไรบ้าง?"
- **ทำไมต้องถาม**: ยิ่งพึ่งพาคนอื่นมาก ยิ่งควบคุมไม่ได้
- **สิ่งที่ได้**: รายการ dependencies + ระดับความเสี่ยงแต่ละตัว
- **ตัวอย่าง**:
  - Third-party API ที่ใช้ → ถ้าเขาเปลี่ยน API / ปิดบริการ → กระทบเราอย่างไร
  - Open-source library ที่ใช้ → ยัง maintain อยู่ไหม? มี known vulnerabilities (ช่องโหว่ที่รู้แล้ว) ไหม?
  - คนในทีม → ถ้าคนที่รู้ส่วนนี้ลาออก → bus factor (จำนวนคนที่ถ้าหายไปแล้วโปรเจกต์จะพัง)

### 10. "ความเสี่ยงเรียงลำดับอย่างไร?"
- **ทำไมต้องถาม**: ไม่สามารถจัดการทุกความเสี่ยงพร้อมกัน → ต้องจัดลำดับ
- **สิ่งที่ได้**: Risk matrix (ตารางความเสี่ยง) ที่จัดลำดับแล้ว
- **วิธีจัดลำดับ**: ใช้ 2 มิติ — Likelihood (โอกาสเกิด) × Impact (ผลกระทบ)
  - สูง × สูง = ต้องจัดการทันที
  - สูง × ต่ำ = monitor (เฝ้าดู)
  - ต่ำ × สูง = เตรียมแผนสำรอง
  - ต่ำ × ต่ำ = ยอมรับได้

## มุมมอง Business Owner

- ถ้าระบบล่ม 1 ชม. เสียเงินเท่าไหร่?
- ถ้าข้อมูลรั่ว ความเสียหายทางชื่อเสียงเป็นอย่างไร?
- มีประกันหรือ SLA (Service Level Agreement — ข้อตกลงระดับบริการ) กับลูกค้าหรือไม่?
- ต้นทุนการป้องกันเทียบกับต้นทุนถ้าเกิดปัญหา?
- มีแผน disaster recovery (การกู้คืนจากภัยพิบัติ) หรือยัง?

## มุมมอง Solution Architect

- ระบบ fail gracefully (พังแบบสง่างาม — เมื่อบางส่วนพัง ส่วนอื่นยังทำงานได้) หรือ fail catastrophically (พังทั้งหมด)?
- มี circuit breaker (ตัวตัดวงจร — หยุดเรียก service ที่ล่มชั่วคราวเพื่อไม่ให้ลุกลาม) ไหม?
- Error handling (การจัดการข้อผิดพลาด) ครอบคลุมทุก scenario ไหม?
- มี monitoring + alerting (การเฝ้าระวัง + แจ้งเตือน) เมื่อเกิดปัญหาไหม?
- Recovery time (เวลาที่ต้องใช้ในการกู้คืนจากปัญหา) ที่ยอมรับได้คือเท่าไหร่?

## Red Flags — สัญญาณว่ายังไม่ผ่าน Gate นี้

- [ ] "ไม่มีความเสี่ยง" → ทุกโปรเจกต์มีความเสี่ยง ถ้าหาไม่เจอ = หาไม่ครบ
- [ ] ไม่มี rollback plan
- [ ] ไม่มี security assessment
- [ ] มี unknowns (สิ่งที่ยังไม่รู้) มากเกินไปแต่ไม่มีแผนหาคำตอบ
- [ ] ไม่ได้จัดลำดับความเสี่ยง
- [ ] ไม่มี mitigation plan (แผนลดความเสี่ยง) สำหรับความเสี่ยงระดับสูง

## Output ที่ต้องได้ก่อนไปต่อ

- [ ] Risk register — ใช้ template จาก `templates/risk-registry.md`
- [ ] Risk matrix (จัดลำดับแล้ว)
- [ ] Mitigation plan สำหรับความเสี่ยงระดับสูง
- [ ] Rollback plan
- [ ] Security assessment
- [ ] รายการ unknowns + แผนหาคำตอบ
- [ ] ระบุว่าเข้า Owner Escalation หรือไม่ (ถ้ามีความเสี่ยงใน critical areas)
