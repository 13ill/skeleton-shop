# Gate 0 — Task Intake: การรับงาน

## วัตถุประสงค์
ทำให้เข้าใจงานที่ได้รับ **อย่างแท้จริง** ก่อนเริ่มคิดเรื่อง solution
Gate นี้ป้องกันการ "กระโดดไปเขียนโค้ดทันที" โดยที่ยังไม่เข้าใจว่าต้องทำอะไร

> ปัญหาที่พบบ่อยที่สุด: โปรแกรมเมอร์รับงานแล้วเริ่มเขียนโค้ดทันที
> โดยไม่ได้ตรวจสอบว่าเข้าใจงานถูกต้องหรือเปล่า

==================================================

## คำถามที่ต้องถามตัวเอง

### 1. "งานนี้คืออะไร — อธิบายด้วยภาษาตัวเองได้ไหม?"
- **ทำไมต้องถาม**: ถ้าอธิบายไม่ได้ = ยังไม่เข้าใจ ถ้ายังไม่เข้าใจ = ทำผิดทิศแน่นอน
- **สิ่งที่ได้**: ความมั่นใจว่าเข้าใจ task ตรงกับคนสั่ง
- **ตัวอย่าง**: "ระบบต้องส่ง email แจ้งเตือนเมื่อ order สถานะเปลี่ยน" ≠ "ทำระบบ email"

### 2. "ใครเป็นคนสั่งงาน? ใครเป็นคนใช้งาน?"
- **ทำไมต้องถาม**: คนสั่งกับคนใช้อาจเป็นคนละคน ต้อง satisfy (ตอบสนอง) ทั้งสองฝ่าย
- **สิ่งที่ได้**: รายชื่อ stakeholder (ผู้มีส่วนได้ส่วนเสีย) ที่ต้องดูแล
- **ตัวอย่าง**: เจ้าของธุรกิจสั่ง แต่พนักงานใช้ → ออกแบบต้องง่ายสำหรับพนักงาน ไม่ใช่เจ้าของ

### 3. "ขอบเขตงานอยู่ตรงไหน — อะไรอยู่ใน อะไรไม่อยู่?"
- **ทำไมต้องถาม**: ถ้าไม่กำหนดขอบเขต งานจะบานปลาย (scope creep — ขอบเขตงานขยายออกไปเรื่อยๆ จนควบคุมไม่ได้)
- **สิ่งที่ได้**: ขอบเขตที่ชัดเจน สามารถพูดได้ว่า "อันนี้ไม่อยู่ใน scope"
- **ตัวอย่าง**: "ทำหน้า login" → ต้องรวม forgot password ด้วยไหม? social login ด้วยไหม?

### 4. "งานนี้ urgent (เร่งด่วน) จริงหรือแค่รู้สึก urgent?"
- **ทำไมต้องถาม**: ความ urgent ที่เกิดจากอารมณ์จะทำให้ข้ามขั้นตอนสำคัญ
- **สิ่งที่ได้**: ระดับความเร่งด่วนที่แท้จริง → จัด priority ได้ถูก
- **ตัวอย่าง**: "ลูกค้าบ่น" อาจเป็น urgent จริง แต่ "อยากได้เร็วๆ" อาจเป็นแค่ความรู้สึก

### 5. "มีข้อมูลอะไรที่ยังขาดอยู่?"
- **ทำไมต้องถาม**: ถ้าเริ่มทำทั้งที่ข้อมูลไม่ครบ จะต้อง rework (ทำซ้ำ) ทีหลัง
- **สิ่งที่ได้**: รายการ unknowns (สิ่งที่ยังไม่รู้) ที่ต้องหาคำตอบก่อน
- **ตัวอย่าง**: ยังไม่มี design mockup, ยังไม่มี API spec, ยังไม่รู้ปริมาณ user

### 6. "เคยมีงานคล้ายๆ นี้มาก่อนไหม?"
- **ทำไมต้องถาม**: อาจมี existing solution (ทางออกที่มีอยู่แล้ว), pattern (รูปแบบ), หรือ lessons learned (บทเรียนจากอดีต)
- **สิ่งที่ได้**: ไม่ต้องเริ่มจากศูนย์ + หลีกเลี่ยงข้อผิดพลาดเดิม
- **ตัวอย่าง**: "ทำระบบ notification" → ดูว่าโปรเจกต์อื่นในองค์กรทำไว้อย่างไร

### 7. "งานนี้เกี่ยวข้องกับ Business Critical Areas หรือไม่?"
- **ทำไมต้องถาม**: ถ้าเกี่ยวกับ payment, auth, data → ต้อง escalate (ยกระดับ) เข้า Owner Review Mode
- **สิ่งที่ได้**: รู้ตั้งแต่ต้นว่าต้อง review ระดับไหน
- **ตัวอย่าง**: "แก้หน้า checkout" → เกี่ยวกับ payment → ต้อง escalate

## มุมมอง Business Owner

เมื่อรับงาน เจ้าของธุรกิจจะถามว่า:
- งานนี้สร้าง value (คุณค่า) อะไรให้ธุรกิจ?
- ถ้าไม่ทำตอนนี้จะเสียอะไร?
- ใช้ resource (ทรัพยากร — เวลา, คน, เงิน) เท่าไหร่?
- คุ้มค่ากับ resource ที่ใช้ไหม?
- มีงานอื่นที่สำคัญกว่าไหม?

## มุมมอง Solution Architect

เมื่อรับงาน สถาปนิกระบบจะถามว่า:
- งานนี้กระทบ architecture (สถาปัตยกรรมระบบ) ตรงไหนบ้าง?
- ต้องเปลี่ยนระบบเดิมมากแค่ไหน?
- มี technical constraint (ข้อจำกัดทางเทคนิค) อะไรบ้าง?
- ต้อง integrate (เชื่อมต่อ) กับระบบอื่นหรือไม่?
- Non-functional requirements (ความต้องการที่ไม่ใช่ feature — เช่น performance, security, scalability) คืออะไร?

## Red Flags — สัญญาณว่ายังไม่ผ่าน Gate นี้

- [ ] ไม่สามารถอธิบายงานด้วยภาษาตัวเอง
- [ ] ไม่รู้ว่าใครเป็นผู้ใช้
- [ ] ขอบเขตงานไม่ชัดเจน
- [ ] มีคำว่า "แค่", "ง่ายๆ", "ทำเร็วๆ" ในการอธิบายงาน
- [ ] ยังมีคำถามสำคัญที่ไม่มีคำตอบ
- [ ] ไม่ได้ตรวจว่าเข้า Owner Escalation หรือไม่

## Output ที่ต้องได้ก่อนไปต่อ

- [ ] สรุปงาน 1-3 ประโยค
- [ ] รายชื่อ stakeholder
- [ ] ขอบเขตงาน (in scope / out of scope)
- [ ] ระดับความเร่งด่วน + เหตุผล
- [ ] รายการคำถามที่ยังต้องหาคำตอบ
- [ ] ระบุว่าเข้า Owner Escalation หรือไม่
