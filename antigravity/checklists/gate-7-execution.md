# Gate 7 — Execution: ลงมือทำ

## วัตถุประสงค์
ลงมือทำ **ตามแผนที่วางไว้** พร้อมตรวจสอบที่ checkpoint
Gate นี้ป้องกันการ "ทำไปเรื่อยๆ หลงทาง" และ "ดันทุรังเมื่อเจอปัญหา"

> ปัญหาที่พบบ่อย: เริ่มทำแล้วออกนอกแผน หรือเจอปัญหาแต่ไม่หยุดวิเคราะห์
> ผลคือใช้เวลาเกินที่ประมาณ คุณภาพต่ำ และสร้าง technical debt

==================================================

## คำถามที่ต้องถามตัวเองระหว่างทำ

### 1. "กำลังทำตาม task list หรือออกนอกทาง?"
- **ทำไมต้องถาม**: ง่ายมากที่จะ "เห็นอะไรก็แก้" → scope creep (งานบานปลาย)
- **สิ่งที่ได้**: Focus (โฟกัส) ที่ตรงตามแผน
- **วิธีจัดการ**: ถ้าเห็นสิ่งที่ต้องแก้แต่ไม่อยู่ใน scope → จดไว้เป็น "TODO ทีหลัง" อย่าแก้ตอนนี้

### 2. "ถึง checkpoint แล้วหรือยัง — ไปถูกทางไหม?"
- **ทำไมต้องถาม**: ถ้าไม่ตรวจ → อาจหลงทางไปไกลก่อนรู้ตัว
- **สิ่งที่ได้**: ความมั่นใจว่ากำลังไปถูกทิศ
- **วิธีตรวจ**: เทียบกับ milestone + definition of done ที่วางไว้ใน Gate 6

### 3. "เจอปัญหาที่ไม่ได้คาดไว้หรือเปล่า?"
- **ทำไมต้องถาม**: ปัญหาที่ไม่คาดอาจเป็นสัญญาณว่า design ไม่ดีพอ → ต้องกลับไป re-design
- **สิ่งที่ได้**: การตัดสินใจว่าจะ "ดันต่อ" หรือ "กลับไปคิดใหม่"
- **กฎ**:
  - ปัญหาเล็ก (ใช้เวลาแก้ < 30 นาที) → แก้ได้เลย + จดบันทึก
  - ปัญหากลาง (ใช้เวลา 30 นาที - 2 ชม.) → หยุดคิดก่อน + อาจต้องกลับ Gate 4
  - ปัญหาใหญ่ (ใช้เวลา > 2 ชม. หรือเปลี่ยน approach) → กลับ Gate 3 + Gate 4 ทันที

### 4. "โค้ดที่เขียนมีคุณภาพหรือเปล่า?"
- **ทำไมต้องถาม**: โค้ดที่คุณภาพต่ำ = technical debt ที่ต้องจ่ายทีหลัง
- **สิ่งที่ได้**: โค้ดที่ maintain (ดูแลรักษา) ได้ในระยะยาว
- **เกณฑ์คุณภาพ**:
  - Readable (อ่านง่าย): คนอื่นอ่านแล้วเข้าใจไหม
  - Named well (ตั้งชื่อดี): ตัวแปร, function, class ตั้งชื่อสื่อความหมายไหม
  - Single responsibility (หนึ่งหน้าที่): แต่ละ function ทำแค่เรื่องเดียวไหม
  - DRY (Don't Repeat Yourself — ไม่ซ้ำซ้อน): มีโค้ดซ้ำไหม
  - Error handling (จัดการข้อผิดพลาด): จัดการ error ครบไหม
  - Comments (ความคิดเห็น): มี comment ที่มีประโยชน์ อธิบาย "ทำไม" ไม่ใช่ "ทำอะไร"

### 5. "เขียน test ควบคู่กับโค้ดหรือเปล่า?"
- **ทำไมต้องถาม**: ถ้ารอเขียน test ทีหลัง → มักจะไม่เขียน
- **สิ่งที่ได้**: Test coverage (ความครอบคลุมของการทดสอบ) ที่ดี → มั่นใจว่าโค้ดทำงานถูก
- **กฎ**: เขียน test ก่อน/พร้อมกับ feature ไม่ใช่หลังจาก feature เสร็จ

### 6. "มี decision ระหว่างทางที่ต้องบันทึกไหม?"
- **ทำไมต้องถาม**: ระหว่างเขียนโค้ดมักเจอสิ่งที่ต้องตัดสินใจเล็กๆ น้อยๆ → ถ้าไม่จด จะลืม
- **สิ่งที่ได้**: Decision log (บันทึกการตัดสินใจ) ที่ครบถ้วน
- **ตัวอย่าง**: "เลือกใช้ date-fns แทน moment.js เพราะ bundle size เล็กกว่า"

### 7. "กำลัง hack/workaround อยู่ไหม?"
- **ทำไมต้องถาม**: ถ้าต้อง hack (แก้แบบ shortcut ไม่ถูกวิธี) หรือ workaround (หาทางเลี่ยง) → อาจเป็นสัญญาณว่า design ไม่ดี
- **สิ่งที่ได้**: การตัดสินใจว่าจะ refactor (ปรับโครงสร้าง) หรือยอมรับ hack
- **กฎ**: ถ้า hack → จดบันทึกเป็น technical debt + กำหนดวันจ่ายคืน

==================================================

## Checkpoint Protocol — สิ่งที่ต้องตรวจที่ milestone แต่ละจุด

เมื่อถึง milestone ที่กำหนดไว้ใน Gate 6:

### ตรวจสอบ
- [ ] ทำตาม task list ครบหรือยัง?
- [ ] Definition of Done ผ่านทุกข้อหรือยัง?
- [ ] Tests ผ่านทั้งหมดหรือไม่?
- [ ] มีปัญหาที่ไม่ได้คาดไว้หรือเปล่า?
- [ ] ยังอยู่ใน scope หรือออกนอก scope?
- [ ] เวลาที่ใช้ตรงกับ estimate หรือเกิน?

### ถ้าเกิน estimate มากกว่า 50%
**หยุด** แล้วถามว่า:
- ทำไมเกิน? → เพราะ unknowns (สิ่งที่ไม่รู้) หรือเพราะ estimate ผิด?
- ต้องปรับแผนไหม?
- ต้องสื่อสารกับ stakeholder ไหม?

==================================================

## มุมมอง Business Owner

- Progress (ความคืบหน้า) เป็นอย่างไร — on track (ตามแผน) หรือไม่?
- มี blocker (สิ่งกีดขวาง) อะไรไหม?
- ต้องเปลี่ยน scope / timeline ไหม?
- มีอะไรที่ต้องสื่อสารกับ stakeholder ตอนนี้ไหม?

## มุมมอง Solution Architect

- โค้ดตาม architecture ที่ออกแบบไว้ไหม?
- มี deviation (การเบี่ยงเบน) จาก design ไหม → ถ้ามี ต้องบันทึก + ประเมิน
- Performance ตามที่คาดไว้ไหม?
- มี code smell (สัญญาณว่าโค้ดมีปัญหา เช่น function ยาวเกินไป, ซ้ำซ้อน, ซับซ้อนเกินจำเป็น) ไหม?

==================================================

## Red Flags — สัญญาณว่ามีปัญหา

- [ ] ทำไปเรื่อยๆ โดยไม่ตรวจที่ milestone
- [ ] เจอปัญหาใหญ่แต่ดันทุรังต่อ
- [ ] ไม่เขียน test
- [ ] มี hack / workaround มากกว่า 2 จุด
- [ ] ใช้เวลาเกิน estimate มากกว่า 50% โดยไม่ปรับแผน
- [ ] ออกนอก scope โดยไม่รู้ตัว
- [ ] แก้ไฟล์เดียวกันหลายครั้งในรอบเดียว → อาจต้อง refactor

## Output ที่ต้องได้ก่อนผ่าน Gate นี้

- [ ] โค้ดที่ทำงานได้
- [ ] Tests ผ่านทั้งหมด
- [ ] Milestone checkpoints ผ่านทุกจุด
- [ ] Decision log ระหว่างทำ (ถ้ามี)
- [ ] Technical debt log (ถ้ามี)
- [ ] เอกสารอัพเดท (ถ้ามีอะไรเปลี่ยนจากแผน)
