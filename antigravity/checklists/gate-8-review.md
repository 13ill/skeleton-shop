# Gate 8 — Review: ตรวจสอบและทบทวน

## วัตถุประสงค์
ตรวจสอบว่าสิ่งที่ลงมือทำ (Execution) มี **คุณภาพ** ตรงตามความต้องการทางธุรกิจ และตรงตามระบบที่ได้ออกแบบไว้ใน Gate 4 และ 5 ก่อนจะส่งมอบหรือทำการ merge (การรวมโค้ด — รวมโค้ดเข้าสู่สาขาหลัก)
Gate นี้ป้องกันการส่งโค้ดที่มี bug, มี technical debt, หรือใช้งานไม่ได้จริงให้กับผู้ใช้หรือองค์กร

> ปัญหาที่พบบ่อย: เขียนโค้ดเสร็จแล้วรีบส่งงาน/merge ทันทีโดยไม่มีการทำ self-review หรือ verification
> ผลคือเกิด bug ในระบบจริง, ระบบทำงานผิดพลาดตาม business logic, หรือต้องทำงานซ้ำ (rework)

## คำถามที่ต้องถามตัวเอง

### 1. "โค้ดและ Feature ทำงานได้ตาม Functional Requirement ครบถ้วนหรือไม่?"
- **ทำไมต้องถาม**: ความสวยงามของโค้ดไม่มีค่าอะไรเลยหาก feature ทำงานได้ไม่ตรงกับที่ธุรกิจต้องการ
- **สิ่งที่ได้**: ความมั่นใจว่าทุกความต้องการใน Gate 0 และ 1 ได้รับการตอบสนองอย่างครบถ้วน
- **วิธีตรวจสอบ**: ย้อนกลับไปดู Acceptance Criteria (เกณฑ์การยอมรับงาน) หรือ Definition of Done ในแผนงาน แล้วทดสอบทีละข้อ

### 2. "เราได้ทดสอบ Edge Cases และ Error Handling แล้วหรือยัง?"
- **ทำไมต้องถาม**: ระบบมักจะพังเมื่อเจอกับเคสที่แปลกประหลาด (edge cases) หรือข้อมูลที่ไม่สมบูรณ์ (invalid input)
- **สิ่งที่ได้**: ความเสถียรและทนทาน (robustness) ของระบบต่อสถานการณ์ที่ไม่เป็นใจ
- **ตัวอย่าง**: การใส่ข้อมูลว่างเปล่า, การกดปุ่มซ้ำๆ อย่างรวดเร็ว (double-submitted forms), ข้อผิดพลาดจาก Network พัง หรือ API ปลายทางล่ม

### 3. "มี Automated Test ครอบคลุมพฤติกรรมที่สำคัญแล้วหรือยัง?"
- **ทำไมต้องถาม**: การทดสอบด้วยมือ (manual test) อาจข้ามรายละเอียด และไม่มีอะไรรับประกันว่าการแก้โค้ดในอนาคตจะไม่ไปทำลายระบบปัจจุบัน (regression — ความถดถอยของระบบจากการปรับปรุงโค้ด)
- **สิ่งที่ได้**: safety net (ระบบความปลอดภัยสำรอง) ที่ช่วยให้มั่นใจเวลาแก้ไขโค้ดครั้งถัดไป
- **เกณฑ์ขั้นต่ำ**: logic หลักของ business (เช่น คำนวณราคาสินค้า, ระบบจ่ายเงิน, flow สมัครสมาชิก) ต้องมี unit หรือ integration tests เสมอ

### 4. "คุณภาพของโค้ด (Code Quality) ผ่านเกณฑ์มาตรฐานหรือไม่?"
- **ทำไมต้องถาม**: โค้ดที่รีบเขียนมักจะมีจุดที่ไม่ได้เก็บกวาดให้เรียบร้อย (code smell — กลิ่นอับของโค้ด หรือโครงสร้างโค้ดที่มีแนวโน้มก่อให้เกิดปัญหา)
- **สิ่งที่ได้**: โค้ดที่อ่านง่าย, ทำความเข้าใจง่าย และดูแลรักษา (maintain) ได้ง่ายในอนาคต
- **สิ่งที่ต้องเช็ค**: ลบ log ที่ไม่จำเป็นออก, ไม่ทิ้งโค้ดที่ comment ไว้โดยไม่ใช้, จัด formatting ให้เรียบร้อย และไม่มี hardcoded values (ค่าที่เขียนตายลงไปในโค้ด — ควรย้ายไปอยู่ใน config หรือตัวแปร)

### 5. "มีการทดสอบความปลอดภัยเบื้องต้น (Security Check) หรือยัง?"
- **ทำไมต้องถาม**: ช่องโหว่ความปลอดภัยเพียงจุดเดียวอาจทำให้ระบบทั้งหมดโดนเจาะ และข้อมูลลูกค้ารั่วไหลได้
- **สิ่งที่ได้**: ความมั่นใจว่าไม่มีช่องโหว่พื้นฐานที่แฮกเกอร์โจมตีได้ง่าย
- **สิ่งที่ต้องเช็ค**: ไม่มีการเก็บความลับ (secrets/API keys) ไว้ในโค้ด, มีการทำ input validation (ตรวจสอบข้อมูลที่กรอกเข้ามา) และทำ authorization check (การตรวจสอบสิทธิ์ว่าผู้ใช้มีสิทธิ์เข้าถึงข้อมูลนั้นจริงหรือไม่)

## ขั้นตอนการทำ Self-Review (Self-Review Protocol)

ก่อนจะส่งมอบงาน ให้ดำเนินตามขั้นตอนเหล่านี้แบบเป็นระบบ:

### ขั้นที่ 1: ตรวจสอบความสอดคล้องกับแผน (Alignment Checklist)
- [ ] สิ่งที่ส่งมอบ ตรงกับ Scope และ Design ที่ตกลงกันไว้
- [ ] หากมีส่วนที่หลุด Scope หรือมีการแก้ไขการออกแบบ ได้มีการขออนุญาตและบันทึกไว้ใน Decision Registry แล้ว

### ขั้นที่ 2: การทดสอบในสภาพแวดล้อมที่เหมือนจริง (Verification Environment)
- [ ] ทดสอบโค้ดบนระบบจำลอง (Staging/Local environment ที่จำลองข้อมูลจริง)
- [ ] ข้อมูลที่ใช้ทดสอบมีความหลากหลาย ครอบคลุมทั้งกรณีปกติ (Happy path) และกรณีผิดปกติ (Sad path)

### ขั้นที่ 3: ตรวจสอบ Automated Tests & Builds
- [ ] รัน test suite ทั้งหมด และต้องผ่าน 100%
- [ ] ทดสอบ build โปรเจกต์ในระบบจริง (Production build) เพื่อให้แน่ใจว่าไม่มี syntax error หรือ configuration ผิดพลาด

## มุมมอง Business Owner

- **User Experience (ประสบการณ์ผู้ใช้)**: ฟีเจอร์นี้ใช้งานง่ายและเป็นธรรมชาติสำหรับผู้ใช้งานทั่วไปหรือไม่?
- **Business Logic (กฎเกณฑ์ทางธุรกิจ)**: ระบบคำนวณเงิน, จัดเก็บข้อมูล หรือส่งอีเมลถูกต้องตามหลักการของธุรกิจร้อยเปอร์เซ็นต์ใช่ไหม?
- **Communication (การสื่อสาร)**: ได้เตรียมเอกสารคู่มือการใช้งาน หรืออธิบายการทำงานให้ทีมงานที่เกี่ยวข้อง (Customer Support, Sales) ฟังหรือยัง?

## มุมมอง Solution Architect

- **Impact Analysis (การวิเคราะห์ผลกระทบ)**: มีการเปลี่ยนแปลงโครงสร้างโค้ดที่อาจกระทบต่อประสิทธิภาพ (performance) ของระบบส่วนอื่นๆ หรือไม่?
- **Technical Debt (หนี้ทางเทคนิค)**: มีโค้ดส่วนไหนที่เป็นการแก้ปัญหาเฉพาะหน้า (workaround/hack) ที่ต้องตามเก็บกวาดภายหลังหรือไม่?
- **Monitoring & Observability (การเฝ้าระวัง)**: ระบบมี logs หรือ telemetry (การเก็บข้อมูลพฤติกรรมระบบ) เพียงพอที่จะระบุปัญหาได้ทันทีที่เกิดข้อผิดพลาดใน production หรือไม่?

## Red Flags — สัญญาณที่ต้องสั่ง "ห้ามผ่านด่าน"

- [ ] โค้ดยังทำงานผิดพลาดในกรณีที่เป็น Happy path (กรณีปกติทั่วไป)
- [ ] โค้ดผ่านการรันในเครื่องตัวเอง แต่คอมไพล์หรือบิลด์ไม่ผ่านในเครื่องอื่น/Staging
- [ ] มีช่องโหว่ความปลอดภัย เช่น เก็บ password เป็น plaintext หรือไม่เช็คสิทธิ์ (missing access control)
- [ ] เขียนโค้ดแก้ไขส่วนอื่นๆ ที่อยู่นอกเหนือขอบเขตงานโดยไม่มีเหตุผลอันควร
- [ ] ไม่มี automated test เลยสำหรับส่วนที่เป็น core logic

## Output ที่ต้องได้ก่อนไปต่อ

- [ ] รายการทดสอบ (Verification Report/Artifact) ที่แสดงผลลัพธ์ว่า feature ทำงานได้ถูกต้อง
- [ ] โค้ดที่ผ่านการรีวิวและได้รับการ Approve (ในกรณีที่ทำงานร่วมกับทีม)
- [ ] บันทึก technical debt หรือจุดที่ต้องปรับปรุงต่อลงใน Registry ของโปรเจกต์
- [ ] การอัพเดท API spec หรือ README เพื่ออธิบายการเปลี่ยนแปลง (ถ้ามี)
